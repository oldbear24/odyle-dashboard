# Odyle API v2 · Discord accounts

PocketBase 0.40.5. JSON requests; authenticated requests use a PocketBase **users** token (`Authorization: Bearer <token>`). HTTPS for hosted connections. No superuser credentials belong in either client.

## Authentication

The browser calls `pb.collection('users').authWithOAuth2({ provider: 'discord', createData: { displayName: 'Adventurer' } })`. PocketBase creates or loads the account linked to that Discord identity; a new account then takes its Discord name through `POST /api/odyle/profile`. Public password registration and password sign-in are disabled, and the `users` collection accepts no direct updates (only the routes below write accounts).

`POST /api/odyle/desktop-code` with `{}` returns `{ code, expiresAt }` to an authenticated account. The 16-character code expires after five minutes, is stored as a digest, and replaces that account's previous unused code. The server cannot show a code again, so the dashboard remembers it in the browser that asked for it (`odyle.pairing` in localStorage, with the account id and `expiresAt`) and its pairing dialog shows the same link again until a minute before it expires; **New link** asks for a new code, which ends the old one. The open dialog learns that the app paired from the account's realtime news (`refresh` on `odyle.user.<accountId>` when a paired PC is added) and `GET /api/odyle/account`: a PC in `devices` whose `pairedAt` is after the code was made used it, and `apps` then shows the character that PC reads. When superusers pause pairing, `desktop-code` answers 400 and the dialog shows that message with the download links.

The dashboard presents a connection link such as `https://your-backend.example/#odyle-pair=ABCDEFGH23456789`. The Windows app extracts the endpoint and code when the user clicks **Paste link & connect** or presses Enter in the pairing input. The fragment is never sent as part of an HTTP request. This link contains the short-lived pairing code, not the account token; only the intended Windows companion should receive it. Base-path deployments are preserved, insecure remote HTTP and embedded URL credentials are rejected. Older apps can still use the raw code with a separate endpoint.

`POST /api/odyle/pair` is public and rate limited. Body `{ code, name? }`, where `name` is the PC's Windows computer name (optional, up to 40 characters; anything else is left out, never refused); response `{ token, record, deviceKey }` for the same account. The code is consumed atomically. Windows stores the device key and token in DPAPI, never Discord credentials.

### Lasting pairing

The link is used once; the pairing lasts. `deviceKey` is a 48-character secret for that one app; the server keeps only its SHA-256 digest (`desktop_devices`). Account tokens last seven days, so the app trades the key for a fresh token whenever it starts, every 24 hours while it runs, and whenever a request answers 401:

| Method / route | Body | Result |
| --- | --- | --- |
| POST `/api/odyle/desktop-sign-in` | `{ deviceKey, name? }` | Public, 30 a minute per client: `{ token, record }` for the paired account; the key's `lastUsedAt` is updated and a given `name` replaces the PC's name. An unknown key answers 401 and the app asks to pair again |
| POST `/api/odyle/desktop-device` | `{ name? }` | Signed-in account: `{ deviceKey }` for a new pairing. Apps paired before device keys existed call it once with their still-valid token |
| POST `/api/odyle/unpair` | `{ deviceKey }` | Public, 30 a minute per client: forgets that key and ends its reader sessions (the app's **Disconnect**); unknown keys answer 200 too |
| POST `/api/odyle/forget-device` | `{ deviceId }` | Signed-in account (**Account & data → Remove PC**): forgets one of its pairings and ends that PC's reader sessions; another account's PC answers 403, an unknown one 404 |

A pairing has no inactivity expiry: it ends when the app disconnects, the PC is removed on the dashboard, the account signs out everywhere or is deleted. An account keeps its 10 most recently used pairings; pairing an eleventh PC drops the one unused longest. The account page lists them (`devices` in `GET /api/odyle/account`) and the data export as `pairedWindowsApps` (`name`, `pairedAt`, `lastSignInAt`), without keys or digests.

A paired app opens its reader session with its key (`POST /api/odyle/session` with `deviceKey`), which ties the session to the PC. Removing the PC deletes those sessions, so the app's next heartbeat answers 403 *Publisher session expired*; its new session with the same key answers 401 *This PC is no longer paired with an account.* and the app asks for a new link, within about a minute. Apps that open sessions without their key (releases before 0.6) stop at their next device sign-in instead: at start-up or within a day.

`POST /api/collections/users/auth-refresh` refreshes a valid token. Tokens last seven days; accounts/data persist independently of token expiry. A Windows app paired by a backend without device keys keeps its connection only by refreshing within those seven days.

## Rooms

| Method / route | Body | Result and authorization |
| --- | --- | --- |
| POST `/api/odyle/create` | `{ name }` | Signed-in user creates owned room; returns `{ room, membership, invites }`, where `invites` are a player and a viewer link for 24 hours, each with its `code` (see [Invite links](#invite-links)) |
| POST `/api/odyle/join` | `{ code }` | Join as reporter/viewer; returns `{ room, membership }`. Repeat join is idempotent: a member gets `{ room, membership, alreadyMember: true }`, also from an expired or used-up link of the room, and uses none of its joins |
| GET `/api/odyle/rooms` | — | `{ rooms, odylePerCube, announcement, readerPaused, readers, clock, notifications, maps, classIcons, kept, serverNow }`: all rooms of the current account; `classIcons` (dashboard 0.48.0) are the [classes' emblems](#class-and-level); `kept` (dashboard 0.44.0) is `{ historyDays, locationDays }`, how long the Odyle history and the places are kept; `announcement` is `{ text, level }` (`info` or `warning`) or `null`, and `readerPaused` is `true` while superusers pause packet readers (see [Reader pause](#reader-pause) and [Server controls](#superuser-monitor-and-settings)). `readers` lists the account's own open reader sessions, latest contact first (up to 10): `{ sessionId, name, lastContactAt }`, where `name` is the Windows computer name of the paired PC that opened the session (empty for a session opened without a device key). The dashboard shows **Reader online on &lt;name&gt;** instead of **Connect reader** while one was in contact in the last 45 seconds and keeps `lastContactAt` current from the `contact` news on the account's topic. `clock` holds the rules of the [Odyle clock](#odyle-clock) |
| GET `/api/odyle/announcement` | — | Public `{ announcement }`, the same message, for pages without an account |
| GET `/api/odyle/snapshot/{id}` | — | Member-only `{ room, members, board, wishlist, runs, week, dungeons, catalog, classRoles, maps, classIcons, announcement, readers, clock, serverNow }`; `board` is the room's [information board](#information-board-and-room-features) or `null`; each member has `displayName` and `characters`; `dungeons` lists the names of the server's dungeon catalog (empty: any name) and `catalog` its entries with their costs (see [Dungeon catalog](#dungeon-catalog)); `classRoles` each class's role in a party (see [Class roles](#class-roles)); `announcement`, `clock` and `readers` (the requesting account's own readers, never another member's) are the same as in `GET /api/odyle/rooms`. A room page that hears `contact` from a reader session it does not list fetches the snapshot once, so a reader started meanwhile is named |
| POST `/api/odyle/sharing` | `{ roomId, characterId, enabled }` | Reporter/owner shares or hides one of their own characters in this room; returns `{ sharedCharacters }`. Without `characterId` (older clients) the choice applies to every character saved at that moment |
| POST `/api/odyle/share-new` | `{ roomId, enabled }` | Reporter/owner turns `shareNew` on or off for this room (viewers get 403): with it on, every character the account saves from then on (by the Windows reader or `POST /api/odyle/character`) is shared there in the same transaction. Returns `{ shareNew }`; `GET /api/odyle/rooms` lists it per room and snapshots per member |
| POST `/api/odyle/wishlist` | `{ roomId, dungeon, wanted, everyone? }` | Adds (`wanted: true`, reporter/owner) or removes (`false`, any member) the caller's own entry for a dungeon; `everyone: true` with `wanted: false` lets the owner or an officer clear that dungeon for all members. Returns `{ wishlist }` |
| POST `/api/odyle/invite-create` | `{ roomId, role?, expiresIn?, maxUses?, label? }` | Owner or officer makes one invite link: `role` `reporter` (default) or `viewer`, `expiresIn` 1800, 86400 (default) or 604800 seconds, `maxUses` 0 (default: no limit) to 50 joins, `label` up to 40 characters. Returns `{ invite, invites }`: the new link with its `code`, the only time it is sent, and the room's open links. A room has up to 20 open links |
| GET `/api/odyle/invites/{id}` | — | Owner-only `{ invites }`: the room's open links (neither expired nor used up), player links first, then the newest, each `{ id, role, label, expiresAt, maxUses, uses, created }`; never a code or digest |
| POST `/api/odyle/invite-revoke` | `{ roomId, inviteId }` | Owner deletes one link of the room: it stops working at once, members who joined with it stay. A link already gone changes nothing. Returns `{ invites }` |
| POST `/api/odyle/invite-preview` | `{ code }` | Public and rate limited: what a link opens, `{ state, room?, inviter?, role?, members? }` (see [Invite links](#invite-links)) |
| POST `/api/odyle/invites` | `{ roomId }` | Owner replaces every link of the room with a new player and viewer link for 24 hours; for dashboards from before links were made one by one |
| POST `/api/odyle/revoke` | `{ roomId, memberId }` | Owner removes another membership |
| POST `/api/odyle/leave` | `{ roomId }` | Non-owner removes their membership; character data remains |
| POST `/api/odyle/close` | `{ roomId }` | Owner deletes room and memberships; character data remains |
| POST `/api/odyle/rename` | `{ roomId, name }` | Owner renames the room (1–60 characters); returns `{ room }` |
| POST `/api/odyle/role` | `{ roomId, memberId, role }` | Owner makes another member `reporter` (player), `officer` or `viewer`; a member made viewer stops sharing characters in the room. Returns `{ membership }` |
| POST `/api/odyle/transfer` | `{ roomId, memberId }` | Owner hands the room to another member, who becomes `owner`; the caller stays as `reporter`. Returns `{ room }` |
| POST `/api/odyle/plan` | see [Planned runs](#planned-runs) | Plans, changes, joins, leaves or cancels a run; returns `{ runs }` |
| POST `/api/odyle/board` | `{ roomId, text }` | Owner or officer writes the room's information board (up to 2,000 characters, lines kept); an empty `text` clears it. Returns `{ board }`. See [Information board and room features](#information-board-and-room-features) |
| POST `/api/odyle/room-features` | `{ roomId, features }` | Owner turns room features on or off: `features` maps `board`, `runs`, `wishlist` and `week` to `true` or `false` (at least one; anything else is 400). Returns `{ room, cancelled }` |
| POST `/api/odyle/discord-webhook` | `{ roomId, webhook?, language?, leads?, startPost?, readiness? }` | Owner connects a Discord channel webhook for run reminders (`language` `en` or `cs`) or disconnects it (`webhook: ''`), and chooses when runs are posted (`leads`: one to three of 5, 10, 15, 30, 60 and 120 minutes; `startPost`: also as a run starts; `readiness`: posts count how many of those going can claim a cube). Without `webhook` only the times change, and `language` alone changes the posts' language: later posts use it and the room's posts still showing a run are edited into it (dashboard 0.27.0, #50). See [Run reminders](#run-reminders). Returns `{ room }` |

**Officers** (`officer`, dashboard 0.24.0, #43) are players the owner trusts to run the room with them: they make, list and revoke invite links (`invite-create`, `invite-revoke`, `GET /api/odyle/invites/{id}`, `invites`), change, cancel and wrap up any run (`plan`), clear a dungeon for everyone (`wishlist` with `everyone`) and connect, change or stop the Discord reminders (`discord-webhook`). Renaming and closing the room, roles, removing members and handing the room over stay with the owner (`rename`, `close`, `role`, `revoke`, `transfer`). Otherwise officers are players: they share characters and count toward the party (every role but `viewer` does, in the dashboard and the Windows app alike).

Invite links last 30 minutes, 24 hours or 7 days; memberships and rooms have no automatic inactivity expiry (accounts can have one, see [Account and data](#account-and-data)). Dashboards share codes as invite links of the form `https://your-dashboard.example/#/join/<code>`; the code stays in the fragment, so no server receives it with the page request, and opening the link while signed in calls `join` with it. An account can own up to 20 rooms and be a member of up to 50; a room holds up to 50 members. Every change answered by the routes above sends the room's realtime news (see [Realtime](#realtime)). Their answers carry the changed state (`wishlist`, `runs`, `sharedCharacters`, `membership` or `room`), which the dashboard draws at once instead of fetching the snapshot again. Sharing is per character: each membership lists the characters its owner linked to that room (`sharedCharacters` in `GET /api/odyle/rooms`). New characters start private everywhere. Room snapshots include only linked characters of other members; members always see all of their own characters, each with `shared: true|false`. Upgrading a backend keeps every character of a membership that shared everything shared. Viewer accounts can maintain private characters, but cannot share them in a viewer-only room. Display-name collisions are resolved by user/member IDs.

### Information board and room features

A room has an information board (dashboard 0.39.0) that its owner and officers write for every member: plain text up to 2,000 characters (UTF-16 units, the 16 KB body limit of `POST /api/odyle/board` holds a full one), whose lines stay. The backend drops invisible characters (as in other free text), the spaces that end a line and more than one empty line in a row; `text` that is not a string is 400, players and viewers get 403. The snapshot's `board` is `{ text, by, at }`: `by` is the account that wrote it last (clients name it from `members`; one who left the room is not named) and `at` when, or `null` for an empty board. `GET /api/odyle/rooms` never carries the board: the Windows app asks for the rooms every 15 seconds. The data download lists the board of a room under its membership when the account wrote it last.

Every room answer's `room` has `features`: `{ board, runs, wishlist, week }`, each `true` while the feature is on. The owner turns them off and on with `POST /api/odyle/room-features` (officers and players get 403); a room keeps only what its owner set, so every feature is on in a room that never set one, and so is a feature added later. A feature turned off disappears for every member and refuses changes with 403:

- `board`: the snapshot's `board` is `null` and `POST /api/odyle/board` is refused; the text stays and shows again when the board is turned on.
- `runs`: the snapshot's `runs` is empty and `plan` is refused. Turning runs off cancels the runs the room lists (until three hours after their start) in the same transaction: their Discord posts are edited to cancelled, or to done for a run under way; the answer's `cancelled` counts the runs ahead it cancelled. With no runs, the room has no reminders, calendar entries or next run in `GET /api/odyle/rooms` either.
- `wishlist`: the snapshot's `wishlist` is empty and `wishlist` is refused; the entries stay and show again when it is turned on. A run planned with `fromWish` while the wishlist is off invites nobody.
- `week`: the snapshot's `week` is `null`.

Installed Windows apps read runs from the snapshot, so a room with runs off reminds of none there either.

### Invite links

An invite link carries a 12-character code. The server keeps only the code's SHA-256 digest, with the link's room, role, maker (`createdBy`), label, expiry, use limit (`maxUses`) and joins so far (`uses`), and sends the code once: in the answer of `create` or `invite-create`. The dashboard that made a link remembers its code until the link expires (`odyle.invites` in localStorage), so only that browser offers the link to copy, while every browser of the owner lists the room's links and revokes them one by one. Each new member counts against the link's use limit. An expired or used-up link refuses new members with *Invite is invalid or expired.*; the expiry job deletes expired links three days later, so until then opening one still names its room.

`POST /api/odyle/invite-preview` with `{ code }` tells whoever opens a link what it opens, before they sign in. It is public and rate limited (30 a minute per client address), and the code goes in the body, never in a URL, so no server or proxy log records it. It answers `{ state: 'valid', room, inviter, role, members }` for a link that still lets someone join (`inviter` is the display name of the room's current owner: the link's maker while they own the room, and the new owner after a hand-over, for links from before makers were kept and for links whose maker deleted the account; `members` is the room's member count), `{ state: 'expired', room }` with the room name only for an expired or used-up link, and `{ state: 'unknown' }` for any other code, revoked links included. The dashboard shows it on `#/join/<code>` before sign-in and after a join that failed, which stays on that page instead of returning to the library, and the join toast names the role. Links shared in Discord unfurl with the page's generic Open Graph tags (title, description and the app icon): the code in the fragment never reaches a link-preview crawler, so no room is named. The backend names the icon by its absolute address under the Application URL (PocketBase **Settings → Application**) when that is a public address; otherwise it stays relative to the page.

### Dungeon wishlist

Each room keeps a list of dungeons its members still need to run. Names are free text (1–60 characters); whitespace is collapsed and names are matched without regard to case, so `fire  temple` joins an existing `Fire Temple` entry, which keeps its first spelling. Repeating an add or removing an entry you are not on changes nothing. A member can be on up to 20 dungeons per room and a room lists up to 50. Entries belong to the membership: leaving, being removed or closing the room deletes them. Viewers see the list but cannot add to it.

The snapshot's `wishlist` is grouped by dungeon, most wanted first, then oldest:

```json
[{ "key": "fire temple", "dungeon": "Fire Temple", "since": "2026-10-13 18:00:00.000Z", "users": ["user-id-1", "user-id-2"] }]
```

`users` are account ids in the order they added the dungeon; clients take display names from `members`. Every change sends the room's realtime refresh, edits in the PocketBase dashboard included. The `room_wishes` collection has no API rules; use the routes above.

### Calendar feed and event links

The snapshot's `week` is the party's week (#42, dashboard 0.35.0): `{ since, spent, cubes }`, what the characters shared in the room spent since the weekly reset (`since`, stored form), in Odyle and in cubes at the Odyle per cube, or `null` when nothing is shared there. A change counts as spent when the app named it a `spend`, or, from apps that do not name changes, when the value dropped from the reading before it within the week. One number for the whole room, never per member. Once a run has started, `spent` on it counts the attendees whose characters shared in the room (their pick, if they picked one) the readers saw spend the run's cost (the catalog cost of its dungeon, else the Odyle per cube) from 15 minutes before its start, as a `spend` the app named; the room then offers **Done** first.

A run can carry `link`, its event elsewhere (Raid-Helper, Apollo, a Discord scheduled event): an https address up to 300 characters, set with `plan` when planning or changing a run (`""` removes it), listed with the runs, shown on the run, in its Discord posts and in Copy for Discord (#35, dashboard 0.34.0).

`POST /api/odyle/calendar` with `{ enabled: true }` makes the account a private calendar feed and answers its `path` once (`/api/odyle/calendar/<token>.ics`); any earlier address stops working. `{ enabled: false }` stops the feed. Only the token's digest is kept (`users.calendarDigest`, hidden), and `GET /api/odyle/account` answers `calendar: { on, since }`. `GET /api/odyle/calendar/<token>.ics` is public: an iCalendar of the runs the account goes to from a day ago to 30 days ahead (dungeon · room, the room link, the event link, a reminder 15 minutes ahead; never notes), for calendars to refresh hourly. A request that succeeds is not written to PocketBase's activity log, so the token stays out of the logs; an unknown token answers 404.

### Slot machine

An easter egg of the dashboard (#107, dashboard 0.32.0): the Odyle logo clicked seven times within three seconds opens `#/slots`. Every account has free spins each daily period (the daily reset hour, UTC): `slots.dailySpins` of the game settings, 3 by default (dashboard 0.42.0). They are kept in `users.cosmetics` (`day`, `daily`) apart from earned spins, given by the first slot call of the period, spent first and never carried over; a lowered allowance applies at once. Playing earns more: the first accepted reading of each character in a daily period gives its account `slots.perCharacter` spins, 1 by default, 0 for none (`characters.spinDay`, single-field updates, so once a day however many readings come); the first visit gives three welcome spins. Superusers set both under **Odyle → Game settings → Slot machine** (`odyle_settings.slots`, `{ dailySpins: 0–20, perCharacter: 0–10 }`). A spin wins with a 15 % chance (`winChance` in the answers; dashboard 0.33.1), rolled on the server with `crypto/rand`, and answers `lost: true` otherwise; a win is a cosmetic item: a rarity (common 60 %, rare 27 %, epic 10 %, legendary 3 %), then one of its items. A duplicate gives a shard, and three shards give a spin back. Nothing is bought and nothing touches Odyle, characters or parties.

| Route | Body | Effect |
| --- | --- | --- |
| POST `/api/odyle/slots` | — | `{ spins, daily, dailySpins, perCharacter, shards, shardsForSpin, winChance, owned, equipped, catalog }`; `spins` counts every usable spin, `daily` of them free ones left today; the first call gives the welcome spins, the first of a daily period the free ones |
| POST `/api/odyle/slot-spin` | — | One spin: the same answer plus `won` (`{ id, kind, rarity, name, value }`) and `duplicate`; 400 without spins |
| POST `/api/odyle/slot-equip` | `{ kind, id }` | Wears an owned item of that `kind` (`color`, `frame` or `badge`), or none with an empty `id` |

`users.spins` and `users.cosmetics` are hidden from every other answer. Room snapshots give each member who wears something a `look` (`{ color?, frame?, badge? }`, the items' values: a CSS colour or gradient, a frame style name, an emoji), shown next to their name in the party rows. The data export lists the account's spins and collection.

### Planned runs

Members plan runs of a dungeon at a time and join them. `POST /api/odyle/plan`:

| Body | Who | Effect |
| --- | --- | --- |
| `{ roomId, dungeon, startsAt, note? }` | owner, players | Plans a run with the caller going. `startsAt` is an ISO time from an hour ago to 60 days ahead, `note` up to 120 characters; up to 20 runs per room still ahead (started runs do not count) |
| `{ roomId, id, going, character? }` | owner, players | `true` joins the run, `false` leaves it. With `character` (one of the caller's own characters shared in this room, else 400) the caller brings that character; joining again changes or drops the pick and keeps the caller's place |
| `{ roomId, dungeon, startsAt, note?, fromWish: true }` | owner, players | Plans the run as above and invites the members who have that dungeon on their wishlist (the planner aside): runs list them as `invited` (account ids) until they answer, and each is told on their account's topic as `invites: [{ runId, roomId, room, dungeon, startsAt, by }]` news, unless their run notices are off (#45, dashboard 0.33.0) |
| `{ roomId, dungeon, note?, call: true }` | owner, players | **Run now** (dashboard 0.41.0): plans the run with the caller going, starting about ten minutes later (the current time plus ten minutes, to the whole minute; `startsAt` is ignored), marks it `called` and invites the players who can come now: every member but the caller and viewers who plays live in the room, or whose character there (their best, as for a run) is expected to hold a cube at the run's cost by its start by the Odyle clock; members without a character in the room are left out. Each invited member is told as for a wishlist invite, with `now: true` in the news, and by Web Push, unless their run notices are off or it is their quiet hours. A room calls once every 30 minutes: another call before then answers 400 (*The party was called less than 30 minutes ago. Answer that run instead.*), while plain runs still plan |
| `{ roomId, id, cant }` | owner, players | `true`: the caller answers they cannot come, which also takes them off the run; `false` takes the answer back; joining again clears it (#45). Runs list them as `cant` (account ids, like `attendees`, which stay those going) |
| `{ roomId, id, dungeon?, startsAt?, note?, link? }` | planner, owner | Changes the run with the same rules as planning; a dungeon that only differs in case or spacing keeps its name, an empty or blank `note` removes the note, a new `startsAt` announces the run on Discord again |
| `{ roomId, id, remove: true }` | planner, owner; after the start also attendees | Cancels the run (after its start: it did not happen) |
| `{ roomId, id, done: true }` | planner, attendees, owner; after the start | Wraps the run up: its attendees' wishes for that dungeon are deleted, then the run (400 before the start) |
| `{ roomId, id, again: true, startsAt? }` | owner, players | Plans the same dungeon and note a week later with the caller going: `startsAt` (the browser sends the same local time, which keeps it across a daylight saving change) or the start plus 7 × 24 hours |

The snapshot's `runs` lists runs until three hours after they started, soonest first; the expiry cron deletes them a day after the start. `planner` and `attendees` are account ids (`planner` is empty once its member left; leaving or removal takes a member off every run), and `picks` maps an attendee's account id to the character they bring, while they still go and still share it in the room (unsharing or deleting the character drops the pick). `attendees` are everyone going, in the order they answered Going; when the [catalog](#dungeon-catalog) gives the run's dungeon a party size and more go, the first that many make its party and `waiting` lists the rest, first come first (dashboard 0.41.0, #45). Those waiting stay in `attendees` and get run reminders, but the run's readiness, its Discord post's count, party ready and the spend it saw count its party only, and **Done** takes the dungeon off the party's wishlists only. `called` marks a run called with **Run now**:

```json
[{ "id": "run-id", "dungeon": "Fire Temple", "startsAt": "2026-10-14 19:00:00.000Z", "note": "Bring potions", "planner": "user-id-1", "attendees": ["user-id-1", "user-id-2"], "picks": { "user-id-2": "character-id" }, "waiting": [], "called": false }]
```

Viewers read runs but cannot plan or join them. The `room_runs` collection has no API rules.

### Run reminders

Each room of `GET /api/odyle/rooms` also says (dashboard 0.25.0, #51) `memberCount`, `liveCount` (the players with a live character now), `partyCubes` (the cubes their party can open now at `odylePerCube`, by the readiness rules of `backend/odyle/readiness.go`) and `nextRun` (`{ id, dungeon, startsAt }` of its next run, or null).

`GET /api/odyle/upcoming` returns `{ runs, notifications, serverNow }`: the runs the signed-in account is going to in the next 24 hours (`?days=` from 1 to 60 reaches further: **Rooms & characters** lists the next 14 days, dashboard 0.25.0), across its rooms, soonest first, each `{ id, roomId, room, dungeon, startsAt, note }`, and the account's [notification settings](#notifications). The dashboard (while open, in a browser that may show notifications) and the Windows app show a notification at the account's reminder times before each start.

### Notifications

Each account keeps one set of notification settings, edited on the dashboard under **Account & data → Notifications** and followed by every browser and Windows app:

```json
{ "channels": { "tray": true, "browser": true, "push": true, "discord": false }, "leadMinutes": [15], "kinds": { "runs": true, "cap": false, "tasks": true, "ready": true }, "capTicks": 1, "quiet": { "from": "", "to": "", "timeZone": "" }, "saved": false }
```

`channels` says where notifications show (the Windows app's tray, browsers with the dashboard open and the permission, and Web Push) and whether the account is mentioned in its rooms' Discord run reminders (`discord`, off until turned on; older clients leave it out); `leadMinutes` are one to three reminder times before a planned run, 1–1440 minutes, different, kept largest first; `kinds` which notifications to show (`runs`: planned runs, `cap`: [cap alerts](#cap-alerts), `ready`: from an hour before a run the account goes to until half an hour after its start, once everyone in its party (two or more; those [waiting for a place](#planned-runs) aside) plays live with enough Odyle for a cube at the run's cost, the `odyle-party-ready` job tells each of them once per start time, on the account's topic as `partyReady: [{ runId, roomId, room, dungeon, startsAt, of }]` news and by Web Push, on until turned off (dashboard 0.29.0, #48); `tasks`: the daily or weekly tasks still open two hours before a reset, which the Windows app shows in its tray from 0.17.0, on until turned off, so settings saved before dashboard 0.25.0 and clients that leave it out keep it on); `capTicks` how many regeneration ticks before the natural pool's cap a cap alert comes, 0 (when it is full) to 8, 1 when left out; `quiet` a daily span (`HH:MM` to `HH:MM`, over midnight when the end is earlier, both empty for none) in the IANA `timeZone` in which none is shown, and a reminder due then is skipped, not delayed. `saved` is `false` while the account keeps the defaults above. `GET /api/odyle/rooms`, `GET /api/odyle/account`, `GET /api/odyle/upcoming` and the export carry them as `notifications`; `POST /api/odyle/notifications` with `{ channels, leadMinutes, kinds, capTicks, quiet }` validates and saves them as a whole (400 with the reason otherwise), returns `{ notifications }` and sends `{ notifications }` on the account's topic. A run within several reminder times when first seen is reminded once, at the smallest.

### Web Push

Run reminders, cap alerts, party ready and calls to a run now (**Run now**) can reach a phone or computer with the dashboard closed. `push` in `GET /api/odyle/account` is `{ publicKey, devices }`: the server's VAPID public key (base64url, empty when it has none), which a browser subscribes with at its push service, and the account's devices with push on, `{ id, device, created, lastOkAt }`.

| Request | Body | Result |
| --- | --- | --- |
| POST `/api/odyle/push-subscribe` | `{ endpoint, keys: { p256dh, auth }, language?, device? }` (a `PushSubscription`'s JSON) | Keeps the subscription for the account (one that another account had moves here; beyond ten devices the oldest go) and returns `{ push }`. Only endpoints of the known push services are accepted (https at `fcm.googleapis.com`, `*.notify.windows.com`, `*.push.services.mozilla.com` or `*.push.apple.com`), else 400; `language` (`en` or `cs`) is the language of its messages, `device` a name up to 60 characters |
| POST `/api/odyle/push-unsubscribe` | `{ endpoint }` | Forgets the account's subscription at that endpoint; returns `{ push }` |
| POST `/api/odyle/push-test` | `{}` | Sends a test to every device of the account and returns `{ sent, push }`, or 400 when none took it |

Each message is `{ title, body, tag, page }`, encrypted for its device (RFC 8291, `aes128gcm`) and signed with VAPID (RFC 8292); the service worker shows it and a click opens `page` (`#/room/<id>`, `#/` or `#/account`). Its tag is the one open dashboards use (`<runId>@<startsAt>@<minutes>` for a run reminder, `cap-<characterId>-<state>` for a cap alert, `invite-<runId>` for a call), so a browser shows one of them. A device its push service forgot (404 or 410) is removed. The `odyle-push` job (every minute) sends run reminders to each account going to a run that has `channels.push` and `kinds.runs` on, at the smallest of its reminder times the run is within, once per start time and never in quiet hours; [cap alerts](#cap-alerts) go out by push as they are found.

### Cap alerts

The `odyle-cap-alerts` job (hourly at :05, after each regeneration tick) projects, with the [Odyle clock](#odyle-clock), the natural pool of every character read in the last 30 days of each account with `kinds.cap` on. It tells the owner once when the pool will be full within `capTicks` ticks (`soon`) and once when it is full (`full`) if it got there without the first; a pool below the threshold again starts over. The last state told is kept on the character (`capAlert`, hidden from every answer), so a restart repeats nothing. Outside the account's quiet hours only: an alert due in them comes after them. It goes to the owner alone, as `{ capAlerts: [{ characterId, characterName, state, base, cap, settled, tick, at? }] }` on the account's topic (its Windows apps show it in the tray and its open dashboards as a browser notification, by `channels`) and by [Web Push](#web-push); never to a room or a Discord channel. `base` is the projected natural pool, `cap` the cap it counts under (`settled` false while it may have a larger one), `at` when it is full (`soon`). It is an estimate: a spend on a PC without the reader is not seen. The job is skipped as `clock` while superusers hide the Odyle clock.

A room owner can connect a Discord channel webhook (`POST /api/odyle/discord-webhook`). Only `https://discord.com/api/webhooks/<id>/<token>` URLs (also `discordapp.com`, `ptb.` and `canary.`) are accepted; the backend posts a test message first and refuses the webhook when Discord does not accept it. The URL is stored in a hidden field: no response, snapshot or export carries it, and rooms report `discordReminders: true|false`, `discordName` (the webhook's name in Discord, read when it is connected), `discordLeads` (minutes before a run, largest first; empty means 15), `discordStartPost` and `discordStatus` (`{ okAt?, error?, errorAt?, dropped?, droppedAt? }`: the last delivery, the last failure, and why a webhook was dropped).

Every minute the `odyle-reminders` job posts each run of those rooms at the room's lead times: at the smallest lead that has come, once for each, but not again when a post for this start came within half that lead again (a run planned 20 minutes ahead is posted once, not for 60 and then 15 minutes), and, with `startPost`, as it starts (in its first five minutes). A post shows the dungeon, Discord timestamps that show in every reader's time zone, the note and the display names of the members going, in the language chosen when connecting, and, when the server's **Application URL** is set (PocketBase settings → Application), links to the room (`<Application URL>/#/room/<id>`). Mentions are switched off, except that the first post of a run pings the Going members who turned the Discord channel on in their [notifications](#notifications) (and are not in their quiet hours): its content lists them as `<@discord id>` and `allowed_mentions.users` names exactly them, never roles or everyone. The backend keeps each post Discord took (`discord_posts`, superusers only: the room, run, Discord message id, lead and a digest of the webhook) for two days. A change of the run's dungeon, start, note or attendees edits its posts in place (the next minute, so a burst of changes makes one edit; edits ping nobody), and a cancelled or done run's posts are marked so. A post is kept before it is sent and forgotten when Discord does not take it, so a failed save never posts twice. A webhook Discord answers 401 or 404 for is dropped (a message deleted in the channel, error 10008, only forgets that post); a webhook replaced since a post leaves that post as it is. When Discord asks to wait (429), the backend waits out up to two seconds once; a longer wait leaves that webhook (every webhook, when Discord names its limit global) alone until it is over, and its runs stay due for a later run. A connection test Discord answers 429 for is refused with "Discord asked to slow down. Try again in a minute."

With `readiness` on (`discordReadiness` on the room, dashboard 0.23.0, #46), each post of a run adds the field **Can claim a cube**: how many of those going can claim one at the start of the run at its dungeon's cost (the server-side port of the run readiness rules, `backend/odyle/readiness.go`, which runs the shared cases of `tests/readiness-vectors.json` like the dashboard and the Windows app): `3/5 by the start (an estimate)` before it starts, `3/5` once it started and `5/5 · party ready` when everyone can. Counts only: never character names or Odyle values, since the channel may include people outside the room. The job re-counts each run's posts every minute until five minutes after the start and edits a post only when what it shows changed (`discord_posts.claims` keeps what it last showed); turning `readiness` off takes the field out of the posts the same way.

### Dungeon catalog

Superusers can keep a catalog of dungeons in `odyle_settings.dungeons` (see [Superuser monitor and settings](#superuser-monitor-and-settings)). While it is empty, wishlist entries and runs take any name. Once it lists dungeons, a new wishlist entry or run must match one of them (regardless of case and spacing) and takes the catalog's spelling; existing wishlist entries can still be joined and left, and existing runs keep their dungeon.

Snapshots report the catalog twice: `dungeons` keeps the plain list of names that dashboards from before the entries read, and `catalog` lists the entries in the same order:

```json
[{ "name": "Abyssal Forge: Ludra", "cost": 80, "partySize": 10, "category": "Sanctuary", "unconfirmed": true }, { "name": "Fire Temple", "cost": 0, "partySize": 0, "category": "", "unconfirmed": false }]
```

`cost` is the Odyle one cube of that dungeon costs, `0` for the server-wide `odylePerCube`; `partySize` is 4, 5, 10 or 20 players, `0` when not set; `category` groups the dungeons (empty: none) and `unconfirmed` marks a cost nobody has checked in game yet. These are game rules superusers keep, never character data. Rooms still report `odylePerCube` as their `cost` (the Windows app reads it). With a catalog, the dashboard's wishlist and run forms pick from it, grouped by category with each cost, and every wishlist entry and run of a listed dungeon shows its cost, party size and the cubes of it the room's party can open now: the room's lowest live player decides, as for the room's own cube count (`src/readiness.js`). A wishlist entry of a dungeon the catalog does not list cannot be planned. Renaming a dungeon in the catalog leaves entries and runs under its old name without a cost.

### Class roles

Superusers keep each class's role in a party in `odyle_settings.classRoles` (Game settings, dashboard 0.41.0, #45), and snapshots report it as `classRoles`:

```json
[{ "class": "Templar", "role": "tank" }, { "class": "Cleric", "role": "healer" }, { "class": "Chanter", "role": "support" }, { "class": "Ranger", "role": "damage" }]
```

Classes are named as PLAYNC names them ([Class and level](#class-and-level)); the role is `tank`, `healer`, `support` or `damage`. Until a superuser saves the table, the backend's default lists AION 2's eight classes (Templar a tank, Cleric a healer, Chanter support, the others damage); a saved empty list is none. A planned run shows its party's make-up by the classes of the characters its members bring (*Make-up: Templar · Cleric · 2× Ranger*, tanks first, with how many classes are unknown) and, once three or more go, *no tank* or *no healer* when the table names a class for that role and the party has none. Classes come from PLAYNC only; players never choose them, and the make-up never stops anyone from going.

## Daily and weekly tasks

Each account keeps a private checklist of daily and weekly tasks in its own order: one list of its own and one for each of its characters (#38), so alts keep their own dailies and weeklies. A task's `character` is the character whose list it is on (with `characterName`), or `""` for the account's own; a character deleted from the account takes its list along. Titles are free text (1–60 characters, inner whitespace collapsed) and each list keeps up to 40 tasks (`limit`). Checking a task stores the time in `doneAt`; the server never unchecks it. Clients show a task as done while `doneAt` is on or after the start of the current period: daily periods begin at `resets.dailyResetHour` UTC, weekly periods on `resets.weeklyResetDay` at that hour (`src/tasks.js` is the reference implementation). Both values come from `odyle_settings` (`dailyResetHour` 0–23, `weeklyResetDay` `sunday`…`saturday`), which superusers edit on the PocketBase dashboard's Odyle page or under *Collections*; the defaults are the Global service's 07:00 UTC and Wednesday.

| Method / route | Body | Result |
| --- | --- | --- |
| GET `/api/odyle/tasks` | — | `{ tasks, resets, characters, templates, limit, serverNow }` of the signed-in account in the account's order (`position`, then oldest first); new tasks go to the end of their list. `characters` are the account's characters (`id`, `characterName`, `server`), the lists it can keep; `templates` the Global list |
| POST `/api/odyle/task` | `{ title, cadence, characterId? }` | Adds a task to the account's list, or to the list of one of its characters; `cadence` is `daily` or `weekly` |
| POST `/api/odyle/task` | `{ templates, characterId? }` | Adds tasks of the Global list by their titles (any case) to one list; a title the list has already is left out, so adding twice changes nothing |
| POST `/api/odyle/task` | `{ id, done }` | `true` stores the current time in `doneAt`, `false` clears it |
| POST `/api/odyle/task` | `{ id, title }` | Renames the task (same rules as adding) |
| POST `/api/odyle/task` | `{ id, move }` | `up` or `down` swaps it with its neighbour in the same list (same cadence and the same account or character list); at either end nothing changes |
| POST `/api/odyle/task` | `{ id, remove: true }` | Deletes the task |

Every POST answers with the same checklist as the GET:

```json
{ "tasks": [{ "id": "task-id", "user": "user-id", "title": "Daily dungeon", "cadence": "daily", "doneAt": "2026-10-13 18:00:00.000Z", "created": "2026-10-13 09:00:00.000Z", "updated": "2026-10-13 18:00:00.000Z" }], "resets": { "dailyResetHour": 7, "weeklyResetDay": "wednesday" }, "serverNow": "2026-10-13T18:00:01.000Z" }
```

The **Global list** is kept by superusers under Game settings (`taskTemplates`: up to 100 `{ title, cadence }`, each title once; empty until they fill it). It applies to tasks added from then on; tasks already on lists stay as they are. A task of another account, or another account's character, answers 403 and an unknown id 404. A change tells the account's own realtime topic (`odyle.user.<accountId>`, so the Windows app and other tabs follow); tasks are not part of room snapshots. The `user_tasks` collection has no API rules; use the routes above.

## Persistent characters and publisher sessions

Own characters can be read with the normal PocketBase `characters` collection API. Others' records and all direct character writes are locked. Shared readings are read via authorized room snapshots; the Windows app reads `GET /api/odyle/snapshot/{id}` for each room to list the party.

### Odyle clock

The natural pool (`parts.base`, see the report above) regenerates by a tick at fixed UTC hours up to a cap; items' Odyle (`parts.bonus`) does not. Clients compute the clock from `clock` in `GET /api/odyle/rooms` and the snapshot, and from each character's last reading; nothing they compute is stored:

```json
{ "tickHours": [1, 4, 7, 10, 13, 16, 19, 22], "tick": 15, "caps": [560, 840], "paused": false }
```

Superusers keep these rules under **Game settings → Odyle clock** (the defaults above); `paused` hides every estimate, for example after a game patch moved the schedule. Characters carry what their own readings showed: `regenTick` the size of their last regeneration tick (0 until one was seen; clients use it instead of `tick`), and `naturalMax` with `naturalMaxAt` the fullest natural pool of the last 30 days (a fuller one replaces it, and after 30 days the next reading does). A character may have every cap `naturalMax` fits under: once it held more than 560 its cap is settled at 840, while it did not the cap is open (560 or 840), unless its account answered the membership question (below): then `answeredCap` settles it. From the last reading, the next ticks add `tick` each until the cap (the smallest one while it is open), so the dashboard shows the next tick, when the natural pool is full (at each cap it may have while the cap is open), that a full pool loses each tick and, for a character not read right now, its estimated value if nothing was spent.

The backend checks the clock: a login reading (`kind` `snapshot` with `parts`) at least one tick after the character's previous reading with `parts` matches when its natural pool equals the projection under a cap the character may have. A spend on a PC without the reader is a miss too, so only many misses at once point to wrong rules. `readers.clock` on the superuser status answers `{ checked, matched, checkedToday, missedToday }` (the last 7 days and the last 24 hours, kept in memory since the server started); most of at least 5 checks of a day missing is an operator alert (see below).

### Membership answer

`POST /api/odyle/membership` with `{ membership }` saves whether the account's game account has the membership: `"yes"`, `"no"`, or `""` while not sure. A new account starts at `"no"` (dashboard 0.38.0); accounts that had not answered got `"no"` then too, or `"yes"` when one of their characters' `naturalMax` was above the smallest of the clock's `caps`. It answers `{ membership }`; `GET /api/odyle/account` and the export carry it too. Anything else answers 400.

The answer settles the natural pool's cap: each of the account's characters carries `answeredCap`, the largest of the clock's `caps` with the membership, the smallest without, and 0 while the answer is open. Rooms, the realtime character news and the Windows app get `answeredCap` with the character; the answer itself never leaves the account. Clients, cap alerts and the clock check use `answeredCap` when it is set and the readings' `naturalMax` otherwise. Characters saved later get the cap of the account's answer, and new caps under Game settings move the answered ones with them. Readings stay as read: a character whose `naturalMax` is above its `answeredCap` contradicts the answer, and the owner's card says so.

### Odyle history

Every reading that changes a character's value (the first one included) is also stored in `character_readings` for as long as Game settings keep it (`historyDays`: 30 days unless a superuser sets 1 to 3,650; the expiry job deletes older changes), with `adapter`, the `parserVersion` of the reading (points saved before adapters were recorded carry their character's latest adapter, `global-reference-v1` on the hosted backend), and from newer Windows apps `parts` (`{ base, bonus }` or `null`), `kind` (`""` when not sent) and `delta` (the change of the total for a `regen`, `spend` or `item`, else `null`). `GET /api/odyle/history/{characterId}` returns the changes of the last 30 days, oldest first, to the character's owner and to members of rooms it is shared in (others get 403, unknown ids 404). Since dashboard 0.44.0 `?days=` asks for another period, 1 day up to `historyDays` (longer asks get all that is kept), and the answer says the period it covers (`days`), how long the history is kept (`keepDays`) and what a thinned answer keeps of its earlier changes (`thinnedTo`, below). Since dashboard 0.35.0 `character` also carries the cap facts (`answeredCap`, `naturalMax`, `regenTick`) and the answer the server's `clock` rules, so the history's **By week** can estimate the hours at the cap and the regeneration lost (#42):

```json
{ "character": { "id": "character-id", "characterName": "Lumina", "value": 140, "confirmed": true }, "readings": [{ "value": 100, "at": "2026-10-13 18:00:00.000Z", "adapter": "global-reference-v1", "kind": "", "delta": null, "parts": null }, { "value": 140, "at": "2026-10-14 09:12:00.000Z", "adapter": "global-reference-v2", "kind": "item", "delta": 40, "parts": { "base": 0, "bonus": 140 } }], "hourlyBefore": null, "thinnedTo": "hour", "days": 30, "keepDays": 30, "serverNow": "2026-10-14T12:00:00.000Z" }
```

The answer always reaches back to the start of its period: 30 days hold at most 1,721 points, a year at most 1,366. Up to 1,000 changes are all listed and `hourlyBefore` is `null`. A character with more lists its newest 1,000 one by one and, before the oldest of them, the last change of each hour (`thinnedTo` `hour`, periods up to 31 days) or of each day (`day`, longer periods); `hourlyBefore` is then the time of that oldest change, so clients know the points before it are thinned. A value holds until the next point either way, so a step chart stays correct to the hour (or day).

`GET /api/odyle/history/{characterId}/changes?days=&page=&perPage=` (same readers) lists every change of the period one by one, a page at a time, newest first: `page` from 1, `perPage` 1–100 (20 by default). Each change is a point as above with `change`, how much it moved the value from the change before it (`null` for the first of the period). The dashboard pages through a thinned period with it:

```json
{ "changes": [{ "value": 140, "at": "2026-10-14 09:12:00.000Z", "adapter": "global-reference-v2", "kind": "item", "delta": 40, "parts": null, "change": 40 }], "page": 1, "perPage": 20, "total": 2, "pages": 1, "days": 30, "keepDays": 30, "serverNow": "2026-10-14T12:00:00.000Z" }
```

The `character_readings` collection has no API rules.

### Location sharing

Off until the account turns it on. `POST /api/odyle/location-sharing` with `{ enabled }` (true or false) saves it and answers `{ shareLocation }`; turning it off sets every character's `location` of the account to `null` (rooms hear of it) and deletes their `character_locations`. `GET /api/odyle/account` carries `shareLocation`, and the `session` and `heartbeat` answers carry it for the Windows app (absent from older backends, meaning off).

The Windows app (0.28.0) sends `POST /api/odyle/location` with `{ sessionId, characterId, adapter, map, x, y, z, heading, source }`: `adapter` is `global-location-v1` (accepted unless switched off under Server controls; others answer 400 *This location adapter is not accepted.*), `map` the game's map id (1–9,999,999), `x`, `y`, `z` the game's world coordinates (at most 1,000,000 from the centre, kept to a tenth), `heading` degrees or `null` (kept as 0–360), `source` `load` (a map load: zone, teleport, channel), `arrival` (the loading screen ends), `flight` (gliding or flying) or `effect` (another effect event of the own character, with some skills). An account that does not share answers `{ shared: false }` and nothing is kept; otherwise `{ shared: true, serverNow }`. Paused readers answer 503, an expired session or another account's character 403.

The latest place is the character's `location`, `null` or `{ map, x, y, z, heading, source, at }`, in room snapshots, realtime character news and the account's own characters. Places are also kept in `character_locations` as long as Game settings keep them (`locationDays`: 30 days unless a superuser sets 1 to 3,650; deleted by the clean-up job): the first, one on another map, one a minute after the last kept, and a load or arrival 100 units or more from it. `GET /api/odyle/locations/{characterId}` answers the owner and members of rooms the character is shared in (others 403, unknown ids 404) with `{ character, shared, location, locations, maps, keepDays, serverNow }`: `locations` newest first, at most 2,000, empty while the owner does not share; `keepDays` is `locationDays`. Since dashboard 0.44.0 `?page=` (from 1) with `perPage` (1–100, 20 by default) answers one page of them instead, and adds `page`, `perPage`, `total` (every kept place) and `pages`.

The game names maps by id only. Superusers name them under Game settings: `maps` is a list of up to 500 `{ id, name, thgl }`, each id once, the name up to 60 characters and `thgl` the map's name as TH.GL lists it, the name its addresses take (`aion2.th.gl/maps/<thgl>`, up to 120 characters starting with a letter or digit: letters, digits, spaces and `_ ' ’ . , : ! ? & ( ) + / -`, as in `Herb Cave / Valka's Nest (+3)`; empty for none). The backend knows TH.GL's AION 2 maps and the places each lists (`backend/odyle/thgl.go`) and fills in what a superuser left out, when maps are saved and read: a map named after a place TH.GL lists (`Altgard`, `Valka's Nest`, `Nightmare Altar`; any case) gets that TH.GL map, a map linked to a TH.GL map of one place gets that place as its name, and a TH.GL map of the list takes TH.GL's spelling; a place two TH.GL maps list links neither, and a map TH.GL adds later is given by its name. Room snapshots, `GET /api/odyle/rooms` and the locations answer carry them as `maps`; `GET /api/odyle/admin/settings` adds `unnamedMaps` (`[{ id, label, characters, lastAt }]`, map ids of the last 30 days' places without a name), `thglMaps` (`[{ name, places }]`, TH.GL's maps in its order, with the places each lists) and `locationAdapters`. Dashboards show a place on TH.GL's embedded map (`https://aion2.th.gl/embed/maps/<thgl>?center=<y>,<x>&zoom=3`: TH.GL swaps the axes, and the name is encoded as one path segment), which the dashboard's Content-Security-Policy allows as its only `frame-src`, with a link to the full map (`aion2.th.gl/maps/<thgl>`) under it as TH.GL's embed terms ask; no map art is stored.

### Character pictures

Each character record carries `portrait`, a file name or empty. Clients load the image from `/api/files/characters/{id}/{portrait}` (the SDK's `pb.files.getURL(record, record.portrait)`); room snapshots include both fields for shared characters only, so other members never receive the link of a private character.

`portrait` is always the character's **official AION 2 portrait**; players cannot set, upload or replace it, and no route writes it. The backend looks up a new character as soon as it is saved through PLAYNC's public Global character search (`api-search.plaync.com/aion2global/search/v2/character`, by name, server id and region, 20 names to a page) and downloads the `profileImageUrl` it lists from `profileimg.plaync.com`; rooms the character is shared in hear of the picture over realtime when it arrives. The search lists every name that contains the keyword, so a lookup reads further pages until it finds the exact name or the last page (by `pagination.total`), five pages at most. Up to ten newly saved characters wait for their lookup at a time; the cron job looks up the others, and those saved while portraits were paused, within a minute or two. It refreshes characters with a portrait daily, rewriting the file only when the image changed. A character the search does not list is tried again an hour, six hours and a day after its first misses, then weekly; a failed search does not count as a miss. Characters no reader has seen for 60 days (or saved that long ago and never read) are not looked up until a reader sees them again. At most two lookups run at a time, and never two for one character. The search server id is rebuilt from the saved server name and region (the game protocol's race × 1000 + region × 100 + server number); NA East and West are both tried, West also when East fails. Characters the search does not list, such as ones on servers the reader cannot name, keep their initials; a failed lookup keeps the last downloaded portrait.

### Class and level

The same search hit gives each character, with no extra request to PLAYNC, its official class and level: `level` (0 until found), `classId` (PLAYNC's `pcId`, four per class, one per race and gender) and `className` (`Chanter`, or empty while that id has no name yet), and `officialId` with `officialRegion` (the search region: `nae`, `naw`, `eu`, `la` or `as`) and `officialServerId`, which together open the character's [armory](#armory) profile (`#/armory/{officialRegion}/{officialServerId}/{officialId}`; all empty while the search has not listed the character). They follow the daily lookup, so a level can be up to a day old. Class names come from PLAYNC's own character pages: the ids the Global pages named on 2026-10-16 are built in, and each profile the armory reads names its class id (the `game_classes` collection, superusers only), so every character with that id is named. Players cannot set or change any of these fields (R1).

Each class's emblem (dashboard 0.48.0) is the one PLAYNC's character pages show (`class_icon_chanter.png`; the Spiritmaster's is `class_icon_elementalist.png`). The server reads PLAYNC's class list when the armory reads a profile of a class without one (at most hourly) and with the nightly `odyle-armory` job, names every class id it lists, and keeps the emblems with the armory's images (`game_classes.icon`). The room list and room snapshots carry `classIcons`, the emblem's file name by class name (`{ "Chanter": "class_icon_chanter.png" }`, only classes the server keeps one of), which `GET /api/odyle/armory-images/{name}` answers. `GET /api/odyle/history/{id}` includes `level` and `className` in its `character` block; the account export keeps them all.

`POST /api/odyle/character` accepts only `{ characterName, server, region }` and returns `{ character }` for the signed-in account. An account keeps up to 30 characters; saving or reporting a new one beyond that answers 400. It saves identity before any reading, with unknown Odyle (`confirmed: false`, `valid: false`, no reading timestamp or source). Repeating the same identity returns the existing record without changing its last value or confidence. Ownership always comes from authentication; extra fields such as `value`, `user`, `source`, `confirmed` and `characterId` are rejected. The Windows app uses this endpoint for automatic game identification.

`GET /api/odyle/account` also answers (dashboard 0.22.0, #49) `usage` (`ownedRooms`, `memberships`, `desktopDevices`, `characters`, to show against `limits`), `retention` (`inactiveAccountDays` and `deleteAfter`, the day the inactive-account clean-up would delete the account if it stayed away, empty while the clean-up is off; since 0.44.0 also `historyDays` and `locationDays`, how long the Odyle history and the places are kept), `paused` (`pairing`, `reminders`), `latestVersion` (the newest Windows release the server knows) and each app's `appVersion`. Room snapshots carry `remindersPaused`, so Room settings can say why no reminder is posted, and (dashboard 0.28.0, #47) `maintenance`: the game's weekly maintenance window superusers set under **Game settings** (`{ day, hour, hours }`, UTC, `maintenance` in `odyle_settings`), or null; a planned run whose first hour overlaps it says so.

`POST /api/odyle/no-odyle` takes `{ characterId }` of one of the account's own characters (another account's answers 403, an unknown one 404) and marks it `odyleLocked: true`: the Windows app read a complete snapshot of the character without its Odyle record, which the game adds at level 22 (odyle-windows#6). It returns `{ character }`. A character that already has a verified reading has Odyle, so it stays unmarked, and the next verified reading of a marked one clears the mark. Rooms show a marked character without a reading as *No Odyle yet · it unlocks at level 22*. Apps send it as its own request after saving the character, so a server from before the action answers 404 and nothing else changes.

`POST /api/odyle/main-character` takes `{ characterId, main }` of one of the account's own characters (another account's answers 403, an unknown one 404, a `main` that is not a boolean 400). `main: true` marks it as the account's main character and clears the mark of the one before, in the same transaction, so an account has at most one; `main: false` clears it. It returns `{ character }`. Characters carry `main` everywhere they are listed (the `characters` collection, room snapshots, realtime news), and the dashboard highlights the main character in the library and in rooms.

`POST /api/odyle/session` with `{}` returns `{ sessionId, sequence: 0, readerPaused }` (see [Reader pause](#reader-pause)). Optional `{ previousSessionId }` rotates that device's session and invalidates its last readings without clearing stored values or other devices' sessions. A paired app also sends `{ deviceKey }`; a key the server no longer knows (or of another account) answers 401, see [Lasting pairing](#lasting-pairing). Newer apps also send `{ appVersion }` (for example `0.6.0.12`; anything else is left out, never refused) for the superuser monitor. A PC runs one app at a time, so a new session with a device key removes the sessions that PC still had open (left by a restart, an update or a crash) without marking their readings stale: the restarted app takes its character over by reporting it again, and otherwise the missing heartbeat turns the reading stale after 45 seconds. The account page and the superuser monitor therefore list one session per paired PC.

`POST /api/odyle/report`:

```json
{
  "sessionId": "publisher-session-id",
  "sequence": 1,
  "characterId": null,
  "characterName": "Your character",
  "server": "Your server",
  "region": "GLOBAL_EU",
  "value": 0,
  "source": "packet",
  "parserVersion": "global-reference-v1",
  "confirmed": true,
  "base": 0,
  "bonus": 0,
  "kind": "snapshot",
  "delta": null
}
```

`base` (the natural pool, which regenerates up to a cap) and `bonus` (what items added) are optional and kept only when both are integers that add up to `value`; the character then carries them as `parts` (`{ base, bonus }`, `null` when the last reading did not send them). `kind` is optional too: `snapshot`, `update`, `regen` (the natural pool alone rose), `spend` or `item`, with `delta` the change of the total (ignored for a snapshot). Anything malformed in these four is left out rather than refused, and Windows apps from before them send none.

Returns `{ character, serverNow }`. Existing `characterId` must belong to the authenticated account and keeps its saved name, server and region: the identity fields in the body are validated but never rewrite an existing character. Without an ID, the identity tuple `(user, region, server, characterName)` finds or creates a character. Value is an integer 0–1,000,000; sequence increases per device session. Supported regions: `GLOBAL_EU`, `GLOBAL_NA`, `GLOBAL_SA`, `GLOBAL_ASIA`. Only packet reports whose `parserVersion` is listed in the backend registry (`backend/odyle/protocols.go`) are accepted; it currently lists `global-reference-v1` and `global-reference-v2`, the Windows companion's Global stream decoders (v2 reads the stat records by Odyle's resource id). Superusers can switch a built-in adapter off or accept another one under [Server controls](#superuser-monitor-and-settings); any other adapter is refused with *This packet adapter has not been validated for Global. No reading was saved.*, a message the Windows app recognizes. Manual reports are always rejected. While packet readers are paused every report is refused (503, or 400 for apps still sending `global-reference-v1`), see [Reader pause](#reader-pause). The Windows app sends a value the first time it reads a character and afterwards only when the value changes, so `lastReadingAt` is the time of the last change (a value re-sent unchanged, for example after the reader paused, keeps that timestamp); its 20-second heartbeat keeps an unchanged value live. Client metadata is not cryptographic proof of a game observation. The synthetic `test-fixture-v1` adapter is approved only in disposable integration-test hooks.

`POST /api/odyle/heartbeat` with `{ sessionId, characterId, reader?, game? }` updates presence for the character only when that session owns its latest reading and packet readers are not paused. It never changes the last reading timestamp and answers `{ serverNow, readerPaused }`. Empty `{}` only returns those. Heartbeats are kept in server memory and written to the database every ten seconds in one transaction (the character's `lastSeenAt`, the session's last contact and expiry); every answer already shows the latest one (snapshots, the `characters` collection, the account page, the superuser monitor). Members of the character's rooms who may see it, and its owner, hear of each heartbeat over realtime (`seen`, see [Realtime](#realtime)) instead of fetching the room again; `GET /api/odyle/rooms` and the snapshot carry `serverNow` for clock correction.

The optional `reader` says what the app's packet reader is doing: `waiting` (no game connection), `listening` (connected, no Odyle read on this connection yet), `midstream` (started after login, or resyncing), `reading` (Odyle read), `problem` (capture failure), `npcap` (Npcap missing or restricted), `two-clients`, `paused` (by the server) or `stopped` (by hand). `game` is the game build the app read from Steam's app manifest, for example `Steam build 25800038` (plain text up to 40 characters, else left out). Unknown values are ignored. Both are kept per reader session in server memory only and shown to superusers (see [Superuser monitor and settings](#superuser-monitor-and-settings)); older apps send neither, and older backends ignore them.

`POST /api/odyle/invalidate` with `{ characterId, sessionId }` marks the latest reading invalid for current readiness if it belongs to that session. It **retains** value, identity and observation timestamp. Confirmed historical values are distinct from current confidence (`valid`). A valid reading is live while presence is newer than 45 seconds, however old the value is; 45 seconds without presence or an invalidated reading is stale, and 90 seconds without presence means offline.

### New packet adapters

A push to `main` ships a Windows release to every installed app at once, so a new decoder name reaches the backend first: list it in `backend/odyle/protocols.go` (or accept it under **Server controls → Also accept**) and deploy that before the Windows release that sends it. Otherwise every updated app has its readings refused. Once the apps in contact run the new release (**Server status** lists them by version), switch the old adapter off under **Server controls → Built-in adapters**. Apps still sending it are refused with the adapter message above, which the Windows app answers by checking for its update at once. A later backend release can then drop the old name from `protocols.go`. History points keep the adapter they were decoded by (`adapter`), so values of a retired decoder can be told apart.

### Reader pause

Superusers can pause every packet reader at once under **Server controls** (`readerPaused` in `odyle_settings`). While it is on, `GET /api/odyle/rooms`, `POST /api/odyle/session` and `POST /api/odyle/heartbeat` answer `readerPaused: true`, and `POST /api/odyle/report` answers 503 with *Packet readers are paused by the server operators.* without saving anything. Sessions, heartbeats and `invalidate` keep working, but a heartbeat no longer keeps a reading live, so every reading turns stale within 45 seconds. Windows apps that know the switch stop capturing and close Npcap, say so on their card and start capturing again by themselves once the flag is `false`. Older apps (adapter `global-reference-v1`) keep capturing; their readings are refused with 400 and the same message instead of 503, because those apps answer any 5xx by opening a new reader session every 20 seconds, while a 400 makes them wait a minute before sending again. They show the message as a refused reading and save again by themselves once the pause ends. Saved values and history stay.

## Armory

Public routes for the armory, signed in or not, with their own rate limits per address: 20 searches and 60 armory requests a minute (its images fall under the general limit of `/api/odyle/`). Everything comes from PLAYNC's official character pages ([Armory](armory.md)); no route writes armory data.

`GET /api/odyle/armory/servers` answers `{ regions: [{ region, elyos, asmodian }] }`: the five Odyle regions (`GLOBAL_NA`, `GLOBAL_NAW`, `GLOBAL_EU`, `GLOBAL_SA`, `GLOBAL_ASIA`) with their server names by race.

**NA-East and NA-West** (odyle-windows#4): the two North American regions have servers of the same names (Siel is 1101 in the East and 1201 in the West). `GLOBAL_NA` is NA-East, and also every NA character saved before the split; `GLOBAL_NAW` is NA-West (from dashboard 0.21.0 and Windows 0.16.0, which sends it for server ids 12xx and 22xx when the server lists it under `/api/odyle/armory/servers`, and `GLOBAL_NA` otherwise). The migration 1791763245 moves the characters PLAYNC's search already found in NA-West (`officialRegion` `naw`), and the daily lookup moves the others when it finds them there, unless the account also has the character under NA-West. The lookup asks only NA-West for `GLOBAL_NAW`, and NA-East then NA-West for `GLOBAL_NA`.

`GET /api/odyle/armory/search?name=&server=&region=` takes a character name (2 to 16 letters or digits), a server name and an Odyle region, as characters keep them. It answers `{ results: [{ name, level, race, server, serverId, region, characterId, class, classIcon }] }`: up to 20 characters PLAYNC's search lists, those named exactly so first. `region` is PLAYNC's search region (`nae`, `naw`, `eu`, `la`, `as`; North America searches both of its own), and `characterId` is decoded. A bad name or an unknown server answers 400. Paused, busy or with PLAYNC's search not answering, it answers 503.

- `skills` are `Active`, `Passive` and `Dp` (stigma) skills; `acquired` says the character learned it and `equipped` that it is on the skill bar.
- `titles.equipped` is the title worn in each category (`Attack`, `Defense`, `Etc`; `name` empty for none), with what it gives when worn (`effects`) and its own stats (`stats`), and how many of the category the character owns.
- `boards[].nodes` are a board's nodes by row (`r`) and column (`c`), with their grade (`g`), type (`t`: `Stat`, `SkillLevel`, `Start`, …) and, when open, `o`; `e` is what a node gives, `n` its name when it has no effect or another type. Boards with no open node have none. `statEffects` and `skillEffects` sum up the open nodes.
- `portrait` and every `icon` name an image the Odyle server keeps (`""` when it has none): `GET /api/odyle/armory-images/{name}` answers it (PNG, JPEG or WebP; icons at most 112 pixels) with `Cache-Control: public, max-age=31536000, immutable`, since a name always shows the same image, and any other name with 404.
- `state` says where the lookup stands:
  - `fresh`: kept and younger than six hours, nothing to do.
  - `queued`: `position` characters are ahead and it takes about `wait` seconds.
  - `fetching`: PLAYNC is being asked right now. `progress` (dashboard 0.47.0, `null` in every other state) says how far: `{ step, done, total, percent }`, where `step` is `profile` (info and equipment), `images` (the icons, the portrait), `items` (each item's page) or `boards` (each open board's page), `done` of `total` is that step, and `percent` the whole lookup (it never goes back, and stays below 100 until the lookup ends).
  - `failed`: `lookupError` says why, and it is tried again after `retryAfter` seconds.
  - `busy`: the queue, or the caller's three places in it, is full.
  - `paused`: superusers paused the armory.
- Opening a profile older than six hours queues it again, and `?refresh=1` does the same once it is 15 minutes old. The kept copy is answered meanwhile.
- Clients ask again after `retryAfter` seconds while the state is `queued`, `fetching` or `busy`. While `queued` it is about when the lookup is due to start (2 to 15 seconds), and 2 while `fetching`.
- A character PLAYNC does not list, a hidden profile, or an id or server outside the region answers 404.

The superuser status answer carries `armory`: `{ profiles, hidden, waiting, fetching, done, failed, lastAt, lastError, lastErrorAt, blockedUntil, paused, images, imageBytes }` (`images` and `imageBytes` count the kept icons and portraits). `armoryPaused` is one of the [server controls](#superuser-monitor-and-settings).

`POST /api/odyle/card` (signed in) saves the look of a player card: `{ region, serverId, characterId, design, finish }` with the profile's search region, server id and PLAYNC character id. It answers the card as the armory route does. Only an account with a character tied to that profile may change it (403), and a holo finish needs the account's membership answer `yes` (403). An unknown design or finish answers 400, and a profile that is not in the armory 404. Every character of the account tied to the profile keeps the choice (`cardDesign`, `cardFinish`); it is no character news for rooms.

## Pages, robots.txt and sitemap.xml

`GET` on any other path answers the dashboard (`backend/web`): a file of the build, or the page named for the path (`backend/odyle/pages.go`). Each page gets a `<base>` back to the dashboard's root, `<meta name="odyle-routes" content="paths">` (the dashboard then uses paths instead of `#/` fragments, `src/routes.js`), its `<title>`, description, Open Graph and Twitter tags, and, with a public Application URL, a canonical link, `og:url`, absolute pictures and schema.org JSON-LD (`WebSite` on the start, `BreadcrumbList` in the armory). Armory profiles (`/armory/<region>/<server id>/<character id>[/skills|daevanion|titles|appearance]`) are named after the kept copy: name, level, class, server, combat power and item level, with the portrait as picture. Signed-in pages (`/room/<id>`, `/tasks`, `/account`, `/slots`), searches (`/armory/find/…`) and profiles not kept yet get `noindex`; hidden profiles and paths that are no page answer 404 with the dashboard, which opens the start. Pages are revalidated by their content hash (ETag).

`GET /robots.txt` lets crawlers read the dashboard and the armory's routes and images, not the rest of `/api/` or `/_/`, and names the sitemap under a public Application URL. `GET /sitemap.xml` lists the public pages (`/`, `/armory`, `/changelog`, `/privacy`, `/demo`) and up to 45,000 kept, visible armory profiles (most recently opened first, with their fetch date as `lastmod`); without a public Application URL it answers 404.

## Windows app release

`GET /api/odyle/windows-release` is public and returns the newest release of the Windows companion as the backend last read it from GitHub:

```json
{ "repository": "oldbear24/odyle-windows", "releasesUrl": "https://github.com/oldbear24/odyle-windows/releases/latest", "latest": { "version": "0.5.0.2", "tag": "v0.5.0.2", "url": "https://github.com/oldbear24/odyle-windows/releases/tag/v0.5.0.2", "publishedAt": "2026-10-13T22:34:09Z", "packages": { "small": { "name": "odyle-0.5.0.2-win-x64.zip", "size": 217557, "url": "https://github.com/oldbear24/odyle-windows/releases/download/v0.5.0.2/odyle-0.5.0.2-win-x64.zip" }, "selfContained": { "name": "odyle-0.5.0.2-win-x64-self-contained.zip", "size": 71595826, "url": "https://github.com/oldbear24/odyle-windows/releases/download/v0.5.0.2/odyle-0.5.0.2-win-x64-self-contained.zip" } } } }
```

`blocked` (dashboard 0.26.0, odyle-windows#19) lists the Windows versions superusers hold back under **Server controls → Windows app updates** (`windowsBlocked` in `odyle_settings`, versions like `0.18.0`, up to 20): apps from 0.18.0 ask their paired backend before each update check, never install a held-back version, and when they run one install the latest release even when it is older. A change reaches running apps at once as `{"windowsBlocked": [...]}` news on every account's topic. Apps that are not paired, and apps before 0.18.0, do not know the list.

The backend calls GitHub's `releases/latest` API when it starts and then at most every ten minutes (every minute while it knows no release, and never before GitHub's rate limit allows) and serves the cached answer, so browsers never contact GitHub and the unauthenticated API limit is never reached. Requests never wait for a lookup while a release is known: they get it while GitHub is asked again in the background, and concurrent requests share one lookup. Later lookups name the known release's ETag, so an unchanged release costs GitHub a 304 that its rate limit does not count. Only versioned, published releases count; only packages with GitHub download links are listed: the x64 ZIPs under `small`/`selfContained`, the per-user installer `odyle-<version>-win-x64-setup.exe` under `installer` and the Windows on ARM ZIPs under `arm64.small`/`arm64.selfContained`. Checksum files are left out because the Windows app verifies its own downloads. When GitHub is unreachable the last known release is kept; without one, `latest` is `null` and clients link `releasesUrl`, GitHub's stable latest-release page. The dashboard shows the link on **Rooms & characters** and the packages in the **Pair Windows app** dialog, the installer first. `ODYLE_WINDOWS_REPOSITORY` points the lookup at a fork; `ODYLE_WINDOWS_RELEASE_URL` replaces the feed URL for tests.

`latest.changes` lists what the release changed, from its notes between `<!-- changes -->` and `<!-- /changes -->` (the release workflows write them from CHANGELOG.md): `[{ "title": "Fixed", "items": ["Updates work again."] }]`, at most 6 groups of 20 entries, with `**bold**` and `` `code` `` as written. It is empty for releases from before the changelog. The dashboard's **What's new** page (`#/changelog`) shows it.

## Superuser monitor and settings

The PocketBase superuser dashboard has an **Odyle** page (UI extension in `backend/admin`, served at `/_/extensions/odyle/`). The monitor, status, jobs and settings routes need a **superuser** token: anonymous requests answer 401 and `users` tokens 403.

| Method / route | Body | Result |
| --- | --- | --- |
| GET `/api/odyle/admin/monitor` | — | `{ serverNow, latestVersion, apps, packets }`; `latestVersion` is the newest Windows release (see [Windows app release](#windows-app-release)), or empty |
| GET `/api/odyle/admin/status` | — | `{ serverNow, startedAt, build, runtime, database, counts, release, versions, traffic, activation, backups, proxy }`, see [Server status](#server-status) |
| GET `/api/odyle/admin/pprof/{name}` | — | Go's profile of the running server, gzipped protobuf for `go tool pprof`: `profile?seconds=30` (CPU), `trace?seconds=5`, `heap`, `allocs`, `goroutine`, `threadcreate`, `block`, `mutex` (block and mutex sampling is off, so those stay empty); unknown names answer 404 |
| GET `/api/odyle/admin/jobs` | — | `{ serverNow, startedAt, jobs }` |
| POST `/api/odyle/admin/jobs/{name}` | — | Runs `odyle-expiry`, `odyle-portraits`, `odyle-reminders` or `odyle-stats` now; `{ result, serverNow, startedAt, jobs }`. `odyle-retention` only runs on its schedule (400), unknown names answer 404, a job still running 400 |
| GET `/api/odyle/admin/settings` | — | `{ settings, defaults, builtInAdapters, acceptedAdapters, seenAdapters, classes, locationAdapters, unnamedMaps }`; `classes` are the class names the armory learned from PLAYNC (`game_classes`), for the class roles; `locationAdapters` and `unnamedMaps` see [Location sharing](#location-sharing) |
| POST `/api/odyle/admin/settings` | `{ odylePerCube?, dailyResetHour?, weeklyResetDay?, inactiveAccountDays?, historyDays?, locationDays?, catalog?, dungeons?, classRoles?, announcement?, announcementLevel?, portraitsPaused?, remindersPaused?, pairingPaused?, readerPaused?, adapters?, clock? }` | Validates and saves the given values, keeps the others; same answer as GET. Bodies up to 64 KB, enough for a full dungeon catalog |
| GET `/api/odyle/admin/retention?days=` | — | `{ days, runAt, inactive, deleted }`: what the inactive-account clean-up would do on its next run (`runAt`, 03:17 UTC) with `days` as the period, before it is saved: `inactive` accounts unused that long by then (by `lastActiveAt`, or by when they were created when they never used Odyle) and the `deleted` ones among them (up to 200 a night). `days` follows the `inactiveAccountDays` rules (400 otherwise); `0` answers no account |
| POST `/api/odyle/admin/vacuum/{name}` | — | Runs SQLite's `VACUUM` on `data` (`data.db`) or `logs` (`auxiliary.db`), then truncates its write-ahead log; `{ result, database }`, `result` being `{ at, ms, beforeBytes, afterBytes, error? }`. Writes to that database wait while it runs; one vacuum runs at a time (400 while another runs), unknown names answer 404 (dashboard 0.40.0) |
| GET `/api/odyle/admin/ui` | — | Public `{ version }`: content hash of the extension page, see below |

`apps` has one entry per open reader session, ordered by account name and then connection time, so heartbeats never reorder them. `device` is the paired PC's name and `appVersion` the version the app sent with its session (both empty when unknown). A running Windows app keeps one session and touches it with every heartbeat and reading, so `lastContactAt` is its last contact, the latest heartbeat included (the page shows 45 seconds without contact as late and 90 as offline). `character` is the character that session read last, or `null`; a character moves to whichever session read it most recently.

```json
{ "sessionId": "session-id", "user": "user-id", "account": "Lumina", "device": "DESKTOP-LUMINA", "appVersion": "0.6.0.12", "connectedAt": "2026-10-14 11:52:10.438Z", "lastContactAt": "2026-10-14 11:52:30.537Z", "readings": 1, "character": { "id": "character-id", "characterName": "Lumina", "server": "Lumiel", "region": "GLOBAL_EU", "value": 390, "confirmed": true, "valid": true, "lastSeenAt": "2026-10-14 11:52:30.537Z", "lastReadingAt": "2026-10-14 11:52:10.481Z", "parserVersion": "global-reference-v1" } }
```

`packets` are the newest 200 requests to every `POST /api/odyle/<action>` route (the `kind` is the action), `pair`, `desktop-sign-in`, `unpair` and `invite-preview` included, oldest first, each with a server-wide increasing `id`. They are kept in server memory only and a restart clears them. Each lists `at`, `kind`, its `source` (`app` for the Windows app's routes `session`, `report`, `heartbeat`, `invalidate`, `character`, `pair`, `desktop-sign-in`, `desktop-device` and `unpair`, `web` for the dashboard's), `user`, `account`, `ok`, the handling time `ms`, `error` when the request was rejected, and only the safe body fields of its route (`backend/odyle/monitor.go`, `shown`), for example `previousSessionId` and `appVersion` (session); `sessionId`, `sequence`, `characterId`, `characterName`, `server`, `region`, `value`, `parserVersion` (report); `roomId` with the room's name for room routes; `taskId` and `runId` for the body `id` of task and plan; `role`, `expiresIn` and `maxUses` (invite-create) and `inviteId` (invite-revoke). Tokens, invite and pairing codes, invite link labels, device keys, webhook URLs, run notes and task titles are never kept. A device sign-in names the account its key belongs to.

```json
{ "id": 4, "at": "2026-10-14T11:52:10.547Z", "kind": "report", "source": "app", "user": "user-id", "account": "Lumina", "ok": false, "ms": 0, "error": "Outdated reading.", "sessionId": "session-id", "sequence": 1, "characterName": "Lumina", "server": "Lumiel", "region": "GLOBAL_EU", "value": 400, "parserVersion": "global-reference-v1" }
```

Superusers subscribe to the realtime topic `odyle.admin.packets` to receive each packet as `{ packet }` the moment it is handled; other clients are refused at subscription and before every delivery.

Settings: `odylePerCube` is an integer 1–1000, `dailyResetHour` 0–23 (UTC), `weeklyResetDay` `sunday`…`saturday`, `inactiveAccountDays` 0 (keep accounts) or 30–3650, `historyDays` and `locationDays` 1–3650 (how many days the Odyle history and the places are kept; 30 by default, and a record without them reads as 30), and `catalog` a list of up to 200 dungeons, each `{ name, cost?, partySize?, category?, unconfirmed? }` or a name alone (no details): `name` 1–60 characters, `cost` an integer 0–1000 (0, the default, is `odylePerCube`), `partySize` 4, 5, 10, 20 or 0 (not set, the default), `category` up to 30 characters and `unconfirmed` true or false; whitespace collapses, and a dungeon listed twice by case and spacing keeps its first entry and spelling. Answers list every dungeon as a full entry in `catalog`, and keep `dungeons` the plain list of names it was before catalog entries. A save may send `dungeons` instead of `catalog`, as admin pages opened before catalog entries do with every save of their game settings: a list of names (entries are taken as in `catalog`) in which each name keeps the details saved for that dungeon, so such a page adds and removes dungeons without wiping their costs. When both are sent, `catalog` is saved. The migration `1791763230_catalog_entries.go` turned a saved list of names into entries at `odylePerCube`. `clock` is `{ tickHours, tick, caps, paused }` (see [Odyle clock](#odyle-clock)): 1–24 different UTC hours 0–23 (saved in order), a tick of 1–1000 Odyle and 1–4 caps of 1–1,000,000, each larger than the one before; all four are sent together. `classRoles` is a list of up to 40 `{ class, role }` (see [Class roles](#class-roles)): `class` 1–40 characters (whitespace collapses), each class once regardless of case, and `role` `tank`, `healer`, `support` or `damage`.

Server controls: `announcement` is one line of up to 300 characters (spaces and line breaks collapse; empty removes it) and `announcementLevel` `info` or `warning`. `portraitsPaused` and `remindersPaused` make those jobs skip their runs; `pairingPaused` refuses `desktop-code` and `pair` with *Pairing new PCs is paused for now. Try again later.* while paired PCs keep signing in. `readerPaused` pauses every packet reader, see [Reader pause](#reader-pause). `adapters` is `{ extra, disabled }`: readings are accepted from the built-in adapters (`backend/odyle/protocols.go`, listed as `builtInAdapters`) that are not disabled, plus up to 20 extra names (letters, digits, `.`, `-`, `_`, up to 80 characters); at least one must remain. `acceptedAdapters` is the resulting list and `seenAdapters` the adapter names in the latest packets with their saved and rejected readings.

The jobs are `odyle-expiry` (every 5 minutes), `odyle-portraits` and `odyle-reminders` (every minute), `odyle-retention` (03:17 UTC, schedule only), `odyle-old-characters` (03:29 UTC: deletes up to 500 characters no reader has read or seen, and not saved, within 365 days, with their history), `odyle-stats` (23:55 UTC: stores the day's activation totals, replacing a row stored the same day) `odyle-health` (every 5 minutes: posts reader-health alerts to the Discord webhook in `ODYLE_ALERT_WEBHOOK`, skipped as `off` without it) `odyle-release` (every 2 minutes: asks GitHub for the newest Windows release; a newer one is news on every account's topic, see [Realtime](#realtime)) `odyle-cap-alerts` (hourly at :05: [cap alerts](#cap-alerts), skipped as `clock` while the Odyle clock is hidden) and `odyle-party-ready` (every minute: [party ready](#notifications), dashboard 0.29.0), `odyle-push` (every minute: [run reminders by push](#web-push)). `jobs` lists each scheduled job with `name`, `manual` (can run by hand), `state` (`active`, `paused` or `off` while inactive accounts are kept), `running`, and since the server started (`startedAt`): `lastRunAt`, `ms`, `byHand`, the last run's `done`, `failed`, `error` or `skipped` (`paused`, `off`; a scheduled run that finds the job still running, from an earlier run or a start by hand, is skipped without a record), and `runs`, `failedRuns`, `totalDone`, `lastFailureAt`, `lastError`. Records live in server memory like packets. Saving creates the `odyle_settings` record if it was deleted. Rooms, room snapshots and the checklist report the new values on their next request.

### Server status

`startedAt` is when the server started. `build` is `{ version, commit, modified, builtAt, go, pocketbase, platform }`: the release version (`dev` for a build without one), its commit and whether the checkout had uncommitted changes, the commit's time, and the Go and PocketBase versions. `runtime` is `{ goroutines, heapBytes, heapObjects, systemBytes, gcCycles, lastPauseMs, pauseTotalMs, cpus, maxProcs, realtimeClients }`. `database` is `{ dataBytes, dataFreeBytes, logsBytes, logsFreeBytes, vacuuming, vacuums }`: the sizes of `data.db` and of PocketBase's log database `auxiliary.db`, each with its write-ahead log, the bytes their free pages take (what a vacuum gives back), the database a vacuum runs on now (`''` while none does) and the last vacuum of each since the server started (`vacuums.data`, `vacuums.logs`, as the vacuum route's `result`; missing before the first). `counts` holds `accounts { total, active24h, active7d }` (by `lastActiveAt`), `characters { total, live }` (a valid reading with a heartbeat in the last 45 seconds), `rooms { total, discordReminders }`, `pairedPcs { total }`, `readerSessions { open, connected }` (in contact within 90 seconds), `plannedRuns { total, upcoming }`, `historyPoints { total }` and `tasks { total }`. `versions` lists the Windows apps in contact within 90 seconds by the `version` their session reported (`''` when the app sent none) with their number of `apps`. `activation` is `{ now, days }`: the activation and feature-use totals computed now, and those the `odyle-stats` job stored for up to the last 30 days (`days`, newest first, each with its UTC `day`, kept in the superuser-only collection `odyle_stats`). Each holds `accounts`, `activeAccounts` (used Odyle in the last 24 hours), `pairedAccounts` (a paired PC, a reader session or a reading), `readingAccounts` (a character with a game reading), `sharingAccounts` (sharing such a character in a room), `roomsReading` (rooms where two or more members' shared characters were read in the last 7 days), `readings` (Odyle changes saved in the last 24 hours), `roomsWithRuns` (a run from 24 hours ago to 7 days ahead), `wishlistEntries`, `taskAccounts`, `discordRooms` and `appVersions`, `[{ version, apps }]` for the apps in contact in the last 24 hours, one per paired PC. They are totals only; no account is named. `backups` is `{ schedule, keep, offHost, setup, count, latest, error }`: PocketBase's backup cron (empty when off) and how many scheduled backups it keeps, whether backups go to S3 storage, why the `ODYLE_BACKUP_S3_*` variables did not apply (empty when they did or are unset), how many backups are stored, the newest `{ name, at, size }` (or `null`) and why they could not be listed (empty when they could); the list is read at most once a minute. `proxy` is `{ headers, leftmost, setup }`: the trusted proxy headers of PocketBase's settings, whether the leftmost address of a list is used, and why the `ODYLE_TRUSTED_PROXY_*` variables did not apply (see [deployment](deployment.md#reverse-proxy)). `release` is the Windows release lookup: `{ repository, version, publishedAt, checkedAt, fetchedAt, error }`, where `checkedAt` is the last time GitHub was asked, `fetchedAt` its last answer, an unchanged one (304) included (both empty before the first), and `error` why the last lookup failed (empty when it worked; a rate limit names when it ends).

`readers` is what the apps' heartbeats reported in the last two minutes: `{ reporting, connected, stuck, statuses, games, refusedAdapters, clock, problems, alerts }`. `statuses` counts the readers by their `reader` value, `connected` those connected to the game (`listening`, `midstream`, `reading`), `stuck` those that have listened for 10 minutes without reading Odyle, `games` the game builds with how many apps read each, `refusedAdapters` the adapter names of recent readings this backend refused, `problems` how many alerts are due and `alerts` whether `ODYLE_ALERT_WEBHOOK` is set. Each `apps` row has `reader`: `{ status, since, game }` or `null`. An alert is due when at least two readers are stuck and they are at least half of those connected to the game (a game patch, most likely), or when readings arrive under a refused adapter, or when most of at least 5 login readings of the last 24 hours did not match the [Odyle clock](#odyle-clock); the `odyle-health` job posts each once when it starts and once when it clears.

`traffic` is the last hour, counted per minute in server memory only (a restart starts it over): every `POST /api/odyle/<action>` route under its `kind` with the packet's `source`, and the Odyle GET routes (`rooms`, `tasks`, `snapshot`, `history`, `invites`, `upcoming`, `account`, `export`, `windows-release`, `announcement`) as `GET <route>` with the source `read`. The superuser routes and requests refused before Odyle handles them (missing sign-in) are not counted, and no account is recorded. `private` is how many of the hour's requests came from a private, loopback or link-local address as rate limits see it (the trusted proxy header's address when one is set): most of them means a reverse proxy whose header is not trusted.

```json
{ "minutes": [{ "at": "2026-10-15T08:30:00.000Z", "app": 4, "web": 1, "read": 3, "rejected": 2 }],
  "total": { "count": 10, "rejected": 2, "averageMs": 2.6, "medianMs": 2, "p95Ms": 7, "maxMs": 7 },
  "routes": [{ "kind": "report", "source": "app", "count": 4, "rejected": 1, "averageMs": 2.5, "medianMs": 2, "p95Ms": 4, "maxMs": 4 }],
  "errors": [{ "kind": "report", "message": "Outdated reading.", "count": 1, "lastAt": "2026-10-15T08:30:53.048Z" }],
  "private": 0 }
```

`minutes` always has 60 entries, oldest first, each with the accepted requests by source and the rejected ones from any source. `routes` lists every route of the hour, busiest first, and `errors` up to 20 rejection reasons, most frequent first. `averageMs` and `maxMs` are exact; `medianMs` and `p95Ms` are upper bounds, because times are counted in steps of 1, 2, 5, 10, 25, 50, 100, 250 and 500 ms, 1, 2.5 and 5 s; they report the slowest time instead when that is lower, and for anything beyond 5 s. `total` has the timings only once a request was counted.

PocketBase serves extension files with a 14-day browser cache. The backend sends the combined entry `/_/extensions.js` (the extension's `main.js`) with `Cache-Control: no-cache`, so browsers fetch it on every load, and the entry imports the page (`odyle.js`, `odyle.css`) under the `version` hash, so a deploy reaches open dashboards on their next reload. Browsers that loaded the entry before it was sent with `no-cache` would keep it for up to 14 days, so the dashboard page `/_/` answers each browser once with `Clear-Site-Data: "cache"` and marks it with the cookie `odyle_entry=1` (path `/_/`); the browser then fetches the current entry. Browsers honour that header only over HTTPS or on localhost.

## Realtime

Subscribe through the PocketBase SDK (`backend/odyle/realtime.go`):

| Topic | Who may subscribe | Messages |
| --- | --- | --- |
| `odyle.room.<roomId>` | members | `{ refresh: true }` after a room, membership, role, sharing, wishlist, run, Discord reminder or display-name change: fetch the snapshot again. `{ refresh: true, characters: [...] }` when only characters changed (a reading, a stale mark, a new portrait, a new character), in their snapshot form with `shared`, and only the ones that member may see: apply them, and fetch the snapshot only for a character not listed yet. `{ refresh: true, removed: true }` to a member who left or was removed; its clients are then unsubscribed from the room and hear nothing more. |
| `odyle.presence.<roomId>` | members | `{ seen: { <characterId>: <lastSeenAt> } }` as the room's readers send heartbeats, for the characters that member may see, at most every two seconds |
| `odyle.user.<accountId>` | that account | `{ refresh: true }` when one of its characters was deleted, its memberships, rooms, tasks, paired PCs, reader sessions or profile changed; `{ characters: [...] }` when only its characters changed or a new one was saved (by `POST /api/odyle/character` or a first reading), as the `characters` collection lists them: apply them, and fetch again for one not listed yet; `{ seen: {...}, contact: { <readerSessionId>: <time> } }` for its readers' heartbeats; and news for every signed-in client: `{ release: { version, publishedAt, url } }` when a newer Windows release is out, `{ announcement: { text, level } \| null }` when the announcement changed, `{ notifications }` when the account saved its [notification settings](#notifications), `{ capAlerts }` with [cap alerts](#cap-alerts) of its characters |
| `odyle.admin.packets` | superusers | see [Superuser monitor and settings](#superuser-monitor-and-settings) |

News is collected and delivered together a moment later (150 ms, heartbeats every two seconds), so a burst of changes is one message per client; each delivery reads the room's members once, for who hears it and which characters each may see. Every room message carries `refresh: true`, so a client that only fetches the snapshot again keeps working. Fetch again on reconnect, as messages may have been missed meanwhile. User and provider tokens are never broadcast. The dashboard fetches its page again only on such news, on reconnect and every five minutes (every 15 seconds while realtime is down). Its health check, every 15 seconds, runs only while realtime is down or a request failed. A hidden tab fetches nothing but its run reminders: news that needs a fetch waits, and the tab fetches once when it is shown again. The announcement comes with the rooms list and room snapshots; other pages ask `GET /api/odyle/announcement` once a minute.
