# Odyle Party Dashboard

A polished AION 2 party dashboard with **Discord sign-in**, persistent character readings, private rooms and PocketBase. Vanilla JavaScript + Vite in the browser; the backend is one Go program built on PocketBase, with no server-side JavaScript and no separate ASP.NET service. The desktop companion lives in [odyle-windows](https://github.com/oldbear24/odyle-windows).

![Dashboard demo](docs/dashboard-preview.png)

## Account and room flow

1. Sign in with Discord. First sign-in creates your account. The browser stays signed in (all tabs, across restarts) until you choose **Sign out of this browser** or skip the dashboard for seven days. A server that cannot be reached (a deploy, a restart, a network drop) never signs you out: the page says so, keeps the sign-in and opens again as soon as the server answers, and the **Connected** label in the top bar follows every refresh.
2. Download the Windows packet reader: **My rooms & characters** links the newest [GitHub release](https://github.com/oldbear24/odyle-windows/releases/latest) as **Windows app &lt;version&gt;** and the **Pair Windows app** dialog offers the per-user installer, the x64 ZIPs and the Windows on ARM ZIPs (the backend reads the release list from GitHub every ten minutes; see [API contract](docs/api.md#windows-app-release)). Once installed, the app updates itself from new releases. Pair it, ideally before logging the character into the game; started later it reads the value at the next Odyle change and needs one relog so the game names the character. It can detect and save the character name, server and region automatically. Saving a character never requires entering Odyle; its value stays unknown until a verified game reading arrives.
3. Create a private room, or join one using an invitation from its owner: open the **invite link** they send (`#/join/<code>`, you join right after signing in) or enter the code under **Join your friends**.
4. Choose which of your characters each room sees under **My rooms & characters → Room sharing** (one switch per character and room), or inside a room: add characters from the **Not in this room** bar above the party and take one out with **Remove from room** on its card. A room lists only the characters added to it, your own included. Other members see the last saved value and timestamp of every shared character, and the Windows app lists the ones that are online. Room and sharing settings live on the dashboard; the Windows app only pairs, reads and displays.
5. Pair your own Windows app using a one-time link from your dashboard account. The pairing lasts: the app stays connected across restarts and weeks switched off until you disconnect it, remove the PC under **Account & data** or sign out everywhere.

The room owner manages the room under **Room settings**: rename it, make members players or viewers, hand the room over (**Make leader**; the previous owner stays as a player), remove members, invite and close it. Closing or leaving a room, removing a member, handing a room over and deleting anything ask for confirmation first.

Each room has a **Dungeon wishlist** under the party: members add the dungeons they still need to run, join an entry with **Need it too** and take themselves off with **Remove me**. The most wanted dungeons come first, and a dot marks members with a live character in the room, so the party sees what it could run now. The room owner can **Clear** an entry for everyone after a run. Viewers can read the list but not add to it. See [API contract](docs/api.md#dungeon-wishlist).

**Planned runs** sit below the wishlist: players pick a dungeon (or **Plan** one from the wishlist), a start time in their local time and an optional note; the party joins with **Going**. Runs are listed soonest first with a countdown until three hours after they started and are deleted a day later; the planner or the room owner can **Edit** (dungeon, time, note) or cancel one. The calendar button downloads the run as an `.ics` file with a reminder 15 minutes ahead. Reminders also come three other ways: the room owner can connect a Discord channel webhook under **Room settings → Discord reminders** (the backend posts each run there 15 minutes before it starts, in English or Czech, with who is going), **Account & data → Run reminders** shows a browser notification while the dashboard is open, and the Windows app reminds from the tray. See [API contract](docs/api.md#planned-runs).

Every character card has a **History** button: a chart and list of every Odyle change in the last 30 days, readable by the owner and by the rooms the character is shared in. See [API contract](docs/api.md#odyle-history).

**Account & data** (sidebar, or the avatar menu on phones) changes the display name rooms see, switches the dashboard between **English and Czech** (detected from the browser, remembered per browser), turns browser run reminders on or off, lists the paired Windows PCs by their computer name with what each is reading and removes one (**Remove PC**: that PC stops within a minute, the others stay signed in), signs out everywhere (every other browser and paired app loses its token), downloads everything stored for the account as JSON and deletes the account. A deleted account's rooms pass to their longest-standing player, or close when there is none. Saved characters can be deleted under **My rooms & characters**. Each account keeps up to 30 characters, owns up to 20 rooms, is a member of up to 50 and keeps 10 paired PCs. See [API contract](docs/api.md#account-and-data).

**Daily & weekly** in the sidebar is each account's own checklist: add the tasks you run every day or week, tick them off, rename them (✎), put them in order (↑ ↓) and remove the ones that no longer apply. Ticked tasks uncheck themselves at the game's reset instead of being deleted: the Global service resets daily at **07:00 UTC** and weekly on **Wednesday** at the same hour, and the page shows both in your local time with a countdown. Superusers can move both on the PocketBase dashboard's **Odyle → Game settings** page (or under *Collections → odyle_settings*: `dailyResetHour`, `weeklyResetDay`). Tasks are private to the account and are not shown in rooms; the Windows app can show your own checklist beside its card and tick tasks off from there. See [API contract](docs/api.md#daily-and-weekly-tasks).

Every character card shows the character's **official AION 2 portrait**, which the backend loads from PLAYNC's public character search as soon as the character is saved and refreshes daily. Pictures always come from the game; players cannot upload or change them. Characters the official search does not list keep their initials. See [API contract](docs/api.md#character-pictures).

Accounts, rooms, memberships and character values persist across sign-outs and server restarts. Leaving or closing a room **does not delete character history**. Stale values remain saved and visible; only fresh readings count toward readiness. Confirmed zero stays zero.

Odyle per cube is one server-wide value (default **40**). Superusers change it on the PocketBase dashboard's **Odyle → Game settings** page (or under *Collections → odyle_settings*: `odylePerCube`); every room's `cost` in the API reports it, so the Windows app follows it too. A room shows each player's best fresh character and its cube count is the **lowest** of those players.

The dashboard is an installable web app; its service worker keeps the page and its files, so it opens without a connection (and then says it cannot reach the server). Readings are never cached. Errors appear in the form that caused them as well as in the message at the bottom, and every control shows a visible keyboard focus.

Every dashboard page has its own URL (`#/`, `#/room/<id>`, `#/tasks`, `#/account`, `#/demo`, and invite links `#/join/<code>`), so reloads and links keep the page, and a fresh visit resumes the last page this browser had open. An open dashboard renews its sign-in every six hours and returns to the welcome page once the server no longer accepts it.

Room invite codes expire after 30 minutes; the owner's browser remembers the codes it created until then, so the invite dialog shows them again after a reload. Membership remains until the user leaves or the room owner removes them. Desktop pairing codes expire after five minutes and can be used once. Viewer invitations give read-only room access; viewers cannot share characters in that room or manage it.

**Manual Odyle entry is disabled; values come from the Windows packet reader.** The app decodes the Odyle snapshot and live updates from the game's own packets and publishes them under the adapter name `global-reference-v1`, which `backend/odyle/protocols.go` lists as accepted. The app sends Odyle when it first reads a character and then only when it changes; the reading stays live while the app's heartbeat reports the game connection and turns stale 45 seconds after that stops. The last value is always kept. Each character is shared per room. The migrations are compiled into the backend (`backend/migrations`) and run at start; they keep the names of the earlier JavaScript migrations, so a database migrated by an earlier release runs none of them again: `1791763204_character_sharing` moves room sharing to individual characters, `1791763205_odyle_settings` adds the Odyle-per-run setting, `1791763206_character_portraits` adds character pictures, `1791763207_room_wishlist` adds the room dungeon wishlist, `1791763208_users_avatar` removes the unused account avatar upload, `1791763209_user_tasks` adds the daily and weekly checklists with the reset-time settings, `1791763210_rate_limits` relaxes the room creation, join and application-route limits, `1791763211_legacy_rooms` drops the unused `rooms`, `members` and `invites` collections left from the first, account-less release, `1791763212_indexes` adds indexes for the hot lookups, `1791763213_account_lifecycle` adds the accounts' last activity and the inactive-account setting, `1791763214_odyle_history` adds Odyle history, `1791763215_room_runs` adds planned runs, `1791763216_dungeon_catalog` adds the dungeon catalog setting, `1791763217_desktop_devices` adds lasting Windows app pairings, `1791763218_profile_lock` closes the `users` collection to direct writes (profiles change only through the checked profile route), `1791763219_device_names` names paired PCs and ties reader sessions to them, `1791763220_run_reminders` adds Discord run reminders and `1791763221_task_order` adds the checklist order, `1791763222_admin_controls` the server controls (the backend needs outbound HTTPS to PLAYNC for official portraits and to Discord for run reminders; see [deployment](docs/deployment.md)). Raw game traffic is never uploaded to the backend. See [packet reader details](https://github.com/oldbear24/odyle-windows/blob/main/docs/packet-reader.md).

## Odyle page in the PocketBase dashboard

The backend adds an **Odyle** page to the PocketBase superuser dashboard (`/_/#/odyle`), a PocketBase UI extension in `backend/admin` that is built into the backend:

- **Apps & packets** lists every connected Windows app (one reader session each, in a fixed order by account) with its account, paired PC, app version (marked when a newer release exists), online/late/offline status, the character it reads and its last Odyle value, and shows the requests as they arrive: from the Windows app reader sessions, readings, 20-second heartbeats, stale marks, character saves and pairings; from the dashboard every room, sharing, wishlist, run, task and account change. Rejected ones show the reason. Filter by Windows app, dashboard or rejected, search the packets (account, character, room, error, ids), click a packet's kind or account (also an account in the app list) to show only those, pause the list to read it, hide heartbeats. A click on a packet shows every field it keeps, with **Copy JSON**; **Export** downloads the packets shown as JSON. Only safe fields are kept (never tokens, codes, keys, webhooks, notes or task titles), and the newest 200 packets live in server memory only, never in the database.
- **Server status** shows the last hour of traffic: requests per minute as a chart (Windows app, dashboard, reads and rejected ones; hover or use the arrow keys for a minute, or open them as a table), each route with its requests, rejections and handling times (average, median, 95 % and slowest), and the rejection reasons, each linking to its packets. Below that, how long the server has been running, the database size, what it holds (accounts active in 24 hours and 7 days, characters with a live reading, rooms, paired PCs, planned runs, history, tasks), the newest Windows release with when GitHub was last asked and why a lookup failed, and the connected Windows apps by version. Under **Server**: the backend's version and commit with its Go and PocketBase versions, goroutines, memory, garbage collection, processors and realtime connections, and Go profiles of the running server (CPU for 30 seconds, heap, allocations, goroutines) to download for `go tool pprof`. Traffic counts every Odyle route, reads included, per minute in server memory only, never which account sent it.
- **Background jobs** shows the scheduled jobs (clean-up every 5 minutes, portrait refresh and Discord reminders every minute, inactive accounts nightly; reminders of different Discord channels post side by side, up to four at a time, and a channel's own runs one after another): when each last ran, how long it took, what it did, how often it ran and failed since the server started and its last failure. The clean-up, portrait refresh and reminders can be run by hand; the account clean-up only runs on its schedule.
- **Game settings** edits the server-wide `odyle_settings`: Odyle per cube and the daily and weekly reset, validated and applied to every room, checklist and the Windows app; the **dungeon catalog** (one name per line; while it lists dungeons, new wishlist entries and planned runs must be one of them and take its spelling; empty allows any name) and **Delete inactive accounts after (days)** (0, the default, keeps every account; 30 or more deletes accounts that have not used the dashboard or the Windows app for that long every night, passing their rooms on as above).
- **Server controls** sets an **announcement** (one line, information or warning) shown above every dashboard page and on the Windows app card; **switches** that pause portrait refresh, Discord reminders or new pairings (paired PCs keep working) without a redeploy; and the accepted **packet adapters**: the built-in ones from `backend/odyle/protocols.go` can be switched off and other names accepted before a deploy, with the adapters seen in the latest packets listed to accept with one click.

Only superusers can open the page; its data routes and live feed refuse every other account. On phones the PocketBase header shows its links as icons, the open page with its name, so **Odyle** stays in reach next to Collections, Logs and Settings. The extension API of PocketBase is still marked experimental. See [API contract](docs/api.md#superuser-monitor-and-settings).

## Run locally

Node.js 22, Go 1.27 and Git:

```powershell
npm ci
npm run backend:build
npm run backend
```

In another terminal:

```powershell
npm run dev
```

Open `http://127.0.0.1:5173`. **Configure Discord before real sign-in:** follow [Discord setup](docs/discord-setup.md). The callback is `http://127.0.0.1:8090/api/oauth2-redirect`. Put provider credentials in ignored `.env.backend`, never in frontend `VITE_*` variables. No Discord bot is needed.

The backend is PocketBase **0.40.5** used as a Go library (`backend/go.mod`) with the Odyle routes, jobs, migrations and superuser page compiled in: `npm run backend:build` builds the server `.runtime/odyle` and the test build `.runtime/odyle-test`; rebuild after changing `backend/`. Both carry the dashboard of the last `npm run build` (copied into `backend/web/dist` for `go:embed`), so the server alone serves it; `--publicDir=dist` serves the folder instead, as `npm run backend` does. Every build of the server uses profile-guided optimisation from `backend/default.pgo`, a CPU profile of the backend under a busy server's traffic: `npm run backend:profile` records a new one (after `npm run backend:build`) by running the test build on a temporary database with Windows readers sending heartbeats and readings and dashboards following their rooms over realtime, and taking 30 seconds through the superuser profile route; refresh it after larger backend changes. Under that traffic the profile saved about 2% of server CPU per request (seven paired runs, from +0.4% to −4.1%); builds take as long and the binary is 1.5% larger. Migrations run on startup. Data is stored in ignored `backend/pb_data/`; keep this directory or your Docker data volume to retain accounts and readings.

To serve UI and API together:

```powershell
npm run build
npm run backend
```

Open `http://127.0.0.1:8090`. For another frontend host, set `VITE_POCKETBASE_URL` in `.env` before building. The backend must allow that exact frontend origin and use HTTPS in production.

## Checks and deployment

```powershell
npm run lint
npm test
npm run test:backend
npm run backend:build
npm run test:integration
npm run build
npm run test:ui
```

`npm run lint` runs ESLint over the dashboard, its tests and the superuser page; CI also requires `gofmt`-formatted Go. `npm test` checks the browser modules and `npm run test:backend` runs `go vet` and the backend's Go tests, which CI also runs under the race detector, followed by ten seconds of fuzzing per fuzz test (the UTF-16 text limits, dates, webhooks, readings and request bodies), `staticcheck` and `govulncheck` (see `.github/workflows/checks.yml` for the commands) (validation of readings, names, runs and webhooks, the last hour's traffic counts, the settings kept in memory, realtime news reaching only who may see it and heartbeats written later; tests that need the database run PocketBase in the test process with every migration applied). `npm run test:ui` drives the built dashboard in Chromium through Playwright against a temporary backend on port 18091 (demo, invite links and typed codes, room settings, Discord reminders, wishlist, sharing, viewers, runs with changes and calendar files, history seen by another member, the checklist, paired PCs, the account page in English and Czech, a room following heartbeats and readings without fetching it again, an unreachable server, offline start, an expired sign-in, the superuser settings page, the packet search and export and the server status); run `npx playwright install chromium` once, set `ODYLE_UI_SHOTS` to a directory to keep screenshots and `ODYLE_UI_WIDTH=390` to check a phone width. Integration tests use synthetic accounts in a temporary backend on port 18090; both run the test build, so run `npm run backend:build` first. They verify the upgrade of an older database, provider configuration, closed password registration, character creation before a reading, duplicate avoidance, multiple saved characters, account isolation, one-use pairing with lasting device keys, realtime access and removal, sequence rejection, and persistence across a real backend restart. Set `ODYLE_WINDOWS_CHECKS` and `ODYLE_WINDOWS_UI_CHECKS` to the Windows repository's corresponding test project paths to exercise both the compiled API client and the native app flow (pairing, automatic character identity, readings and sharing). A synthetic packet adapter is approved only in the disposable test backend; these tests do not validate the Global protocol. Test-only routes exist only in the test build (Go build tag `odyletest`, `backend/odyle/testing.go`) and are **not included in production**. Live Discord login requires your own provider credentials.

GitHub Actions runs the checks on every push; pushes to `main` also publish a Linux container image and a release with the server for Linux and Windows. The **Windows companion checks** workflow runs the Windows app's API and UI checks from [odyle-windows](https://github.com/oldbear24/odyle-windows) against this backend weekly, on demand and when `backend/` changes on `main`. [Deployment](docs/deployment.md), [API contract](docs/api.md), [privacy](docs/privacy.md).

The account migration locks the previous MVP's guest collections. New accounts use `users`, `party_rooms`, `room_members`, `characters`, `character_readings`, `publisher_sessions`, `room_invites`, `room_wishes`, `room_runs`, `user_tasks`, `desktop_codes` and `desktop_devices`. Old guest tokens cannot use the new API. Guest data is preserved as locked records during migration rather than silently erased.

Fonts use Google Fonts with system fallbacks; there is no analytics. Remove the CSS font import or self-host fonts for a fully self-contained UI.
